# Требования: Исправление парсинга callback-данных при удалении вложений

## Введение

Данный документ описывает требования к исправлению критического бага в обработке callback-данных при удалении и отмене удаления вложений в Telegram-боте семейного календаря. Проблема возникает из-за несоответствия между форматом callback-данных, генерируемых в `KeyboardService`, и логикой парсинга в `AttachmentCallbackHandler`.

## Глоссарий

- **Callback_Data**: строка данных, передаваемая при нажатии inline-кнопки в Telegram
- **AttachmentCallbackHandler**: обработчик callback-запросов для работы с вложениями
- **KeyboardService**: сервис для создания клавиатур с inline-кнопками
- **Event_ID**: уникальный идентификатор события в системе
- **Attachment_ID**: уникальный идентификатор вложения в системе
- **Payload**: часть callback-данных после префикса "attach_file_"

## Требования

### Требование 1: Корректный парсинг callback-данных для отмены удаления

**User Story:** Как пользователь, я хочу иметь возможность отменить удаление вложения, чтобы избежать случайной потери данных.

#### Acceptance Criteria

1. WHEN пользователь нажимает кнопку "Отмена" в диалоге подтверждения удаления вложения, THEN система SHALL корректно распарсить callback-данные формата "attach_file_cancel_delete_{eventId}"
2. WHEN система парсит callback-данные "attach_file_cancel_delete_{eventId}", THEN система SHALL извлечь action="cancel", subAction="delete" и eventId из payload
3. WHEN система обрабатывает действие "cancel" с subAction="delete", THEN система SHALL вызвать метод handleCancelDelete с корректным eventId
4. WHEN обработка отмены удаления завершена успешно, THEN система SHALL вернуть пользователя к списку вложений события

### Требование 2: Корректный парсинг callback-данных для подтверждения удаления

**User Story:** Как пользователь, я хочу иметь возможность подтвердить удаление вложения, чтобы окончательно удалить ненужный файл.

#### Acceptance Criteria

1. WHEN пользователь нажимает кнопку "Да, удалить" в диалоге подтверждения удаления вложения, THEN система SHALL корректно распарсить callback-данные формата "attach_file_confirm_delete_{eventId}_{attachmentId}"
2. WHEN система парсит callback-данные "attach_file_confirm_delete_{eventId}_{attachmentId}", THEN система SHALL извлечь action="confirm", subAction="delete", eventId и attachmentId из payload
3. WHEN система обрабатывает действие "confirm" с subAction="delete", THEN система SHALL вызвать метод handleConfirmDelete с корректными eventId и attachmentId
4. WHEN подтверждение удаления завершено успешно, THEN система SHALL удалить вложение и отобразить обновленный список вложений

### Требование 3: Обработка ошибок парсинга

**User Story:** Как разработчик, я хочу получать понятные сообщения об ошибках при некорректном формате callback-данных, чтобы быстро диагностировать проблемы.

#### Acceptance Criteria

1. WHEN система получает callback-данные с некорректным форматом для действия "cancel", THEN система SHALL логировать предупреждение с деталями ошибки
2. WHEN система получает callback-данные с некорректным форматом для действия "confirm", THEN система SHALL логировать предупреждение с деталями ошибки
3. WHEN система не может распарсить callback-данные, THEN система SHALL отправить пользователю сообщение "❌ Ошибка: некорректный формат"
4. IF система получает callback-данные с недостаточным количеством частей, THEN система SHALL обработать ошибку без выброса исключения

### Требование 4: Совместимость с существующим форматом callback-данных

**User Story:** Как разработчик, я хочу сохранить совместимость с существующим форматом callback-данных, чтобы не нарушить работу других частей системы.

#### Acceptance Criteria

1. WHEN система обрабатывает callback-данные для других действий с вложениями (list, add, view, delete, back), THEN система SHALL продолжать работать без изменений
2. WHEN KeyboardService генерирует callback-данные для кнопок подтверждения и отмены, THEN формат данных SHALL оставаться неизменным
3. WHEN система парсит payload, THEN она SHALL корректно обрабатывать как простые действия (одна часть), так и составные действия (две части)
4. WHEN система обрабатывает составные действия, THEN она SHALL корректно определять позицию eventId и attachmentId в зависимости от количества частей

### Требование 5: Логирование и отладка

**User Story:** Как разработчик, я хочу иметь подробное логирование процесса парсинга callback-данных, чтобы легко диагностировать проблемы в продакшене.

#### Acceptance Criteria

1. WHEN система начинает обработку callback-запроса, THEN система SHALL логировать полные callback-данные на уровне DEBUG
2. WHEN система парсит payload, THEN система SHALL логировать извлеченные части (action, subAction, eventId, attachmentId) на уровне DEBUG
3. WHEN система обнаруживает некорректный формат, THEN система SHALL логировать детали ошибки на уровне WARN
4. WHEN система успешно обрабатывает callback, THEN система SHALL логировать результат на уровне DEBUG
