# Документ проектирования

## Обзор

Исправление логики подсчета событий в команде `/stats` для отображения только активных событий, исключая завершенные, удаленные и черновики. Это обеспечит согласованность между статистикой и списком событий в `/my_events`.

## Архитектура

Изменения затронут три компонента:

1. **EventRepository** - добавление новых методов подсчета с фильтрацией по статусу
2. **StatisticsService** - изменение логики подсчета для использования только активных событий
3. **StatsCommandHandler** - обновление отображения статистики

Архитектурный подход:
- Минимальные изменения в существующем коде
- Добавление новых методов вместо изменения существующих для обратной совместимости
- Использование Spring Data JPA для автоматической генерации запросов

## Компоненты и интерфейсы

### EventRepository

Добавление новых методов для подсчета только активных событий:

```java
/**
 * Подсчитывает количество активных событий семьи в диапазоне дат.
 * Исключает завершенные, удаленные и черновики.
 */
int countByFamilyIdAndEventDateBetweenAndStatus(
    Long familyId,
    LocalDate startDate,
    LocalDate endDate,
    Event.EventStatus status
);

/**
 * Подсчитывает количество активных персональных/семейных событий пользователя.
 */
int countByUserIdAndEventDateBetweenAndIsPersonalAndStatus(
    Long userId,
    LocalDate startDate,
    LocalDate endDate,
    Boolean isPersonal,
    Event.EventStatus status
);
```

### StatisticsService

Изменение метода `getMonthlyStatistics`:

**Текущая логика:**
- `totalEvents` = все события в диапазоне дат (включая COMPLETED, DELETED, DRAFT)
- `activeEvents` = события со статусом ACTIVE
- `completedEvents` = события со статусом COMPLETED

**Новая логика:**
- `totalEvents` = только события со статусом ACTIVE (исключая COMPLETED, DELETED, DRAFT)
- `activeEvents` = события со статусом ACTIVE (без изменений)
- `completedEvents` = события со статусом COMPLETED (без изменений)
- `familyEvents` = семейные события со статусом ACTIVE
- `personalEvents` = персональные события со статусом ACTIVE

### StatsCommandHandler

Обновление отображения:
- "Всего событий" теперь показывает только активные события
- Процент завершения рассчитывается от суммы активных и завершенных событий
- Добавление пояснения, что статистика показывает только активные события

## Модели данных

Используются существующие модели:

**Event.EventStatus:**
- ACTIVE - активное событие (учитывается в статистике)
- COMPLETED - завершенное событие (учитывается отдельно)
- DELETED - удаленное событие (не учитывается)
- DRAFT - черновик (не учитывается)

## Свойства корректности

*Свойство - это характеристика или поведение, которое должно выполняться во всех допустимых выполнениях системы - по сути, формальное утверждение о том, что система должна делать. Свойства служат мостом между человекочитаемыми спецификациями и машинопроверяемыми гарантиями корректности.*

### Свойство 1: Подсчет только активных событий

*Для любого* набора событий семьи в заданном диапазоне дат, значение "Всего событий" в статистике должно быть равно количеству событий со статусом ACTIVE, исключая события со статусами COMPLETED, DELETED и DRAFT.

**Проверяет: Требования 1.1, 1.2**

### Свойство 2: Согласованность со списком событий

*Для любого* пользователя и месяца, количество событий в статистике /stats должно соответствовать количеству событий, отображаемых в /my_events.

**Проверяет: Требования 1.4**

### Свойство 3: Подсчет по типам только активных событий

*Для любого* набора событий, количество семейных событий и количество персональных событий в статистике должны учитывать только события со статусом ACTIVE, исключая COMPLETED, DELETED и DRAFT.

**Проверяет: Требования 2.1, 2.2, 2.4**

### Свойство 4: Инвариант суммы по типам

*Для любого* набора событий, сумма семейных и персональных событий должна быть равна значению "Всего событий".

**Проверяет: Требования 2.3**

### Свойство 5: Формула процента завершения

*Для любого* набора активных и завершенных событий, процент завершения должен рассчитываться как (количество завершенных / (количество активных + количество завершенных)) * 100, исключая из расчета события со статусами DELETED и DRAFT.

**Проверяет: Требования 3.1, 3.4**


## Обработка ошибок

### Валидация входных данных

- Проверка корректности месяца (1-12) - уже реализована в StatisticsService
- Обработка случая отсутствия пользователя или семьи

### Обработка граничных случаев

1. **Нет событий в месяце**: отображение "0" для всех счетчиков
2. **Только завершенные события**: "Всего событий: 0", но "Завершено" показывает количество
3. **Только удаленные/черновики**: "Всего событий: 0"
4. **Деление на ноль при расчете процента**: возврат 0%

### Логирование

- Логирование запросов статистики с параметрами (familyId, userId, year, month)
- Логирование результатов подсчета для отладки
- Логирование ошибок при получении статистики

   - Тест исключения завершенных событий из totalEvents
   - Тест исключения удаленных событий из totalEvents
   - Тест исключения черновиков из totalEvents

   - Тест подсчета персональных событий только ACTIVE

Каждый property-based тест должен выполнять минимум 100 итераций для обеспечения надежности.

### Интеграционные тесты

1. **StatsCommandHandlerIntegrationTest**:
   - Тест полного цикла: создание событий → вызов /stats → проверка результата
   - Тест согласованности между /stats и /my_events
   - Тест с реальной базой данных (Testcontainers)

## Миграция данных

Миграция данных не требуется, так как изменяется только логика подсчета, структура БД остается без изменений.

## Влияние на производительность

Минимальное влияние:
- Новые методы репозитория используют индексы по familyId, userId, eventDate и status
- Количество запросов к БД не увеличивается
- Запросы остаются простыми и эффективными

## Обратная совместимость

Изменения обратно совместимы:
- Существующие методы репозитория не изменяются
- Добавляются новые методы для более точного подсчета
- API команды /stats не меняется
- Формат ответа остается прежним, меняется только логика подсчета
