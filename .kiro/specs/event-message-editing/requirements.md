# Requirements Document

## Introduction

Данный документ описывает требования к функции редактирования сообщений о событиях в Telegram боте семейного календаря. В настоящее время при редактировании события (изменении названия, даты, времени, описания и других полей) бот отправляет новое сообщение в чат, что приводит к засорению чата множеством сообщений. Требуется изменить поведение так, чтобы бот обновлял существующее сообщение о событии вместо отправки нового.

## Glossary

- **Event**: Событие в календаре, содержащее название, дату, время, описание и другие атрибуты
- **Message**: Сообщение в Telegram чате, содержащее информацию о событии
- **Message_ID**: Уникальный идентификатор сообщения в Telegram
- **Edit_Message**: Операция обновления существующего сообщения в Telegram через API метод editMessageText
- **EventCallbackHandler**: Обработчик callback queries для операций с событиями
- **TelegramMessageService**: Сервис для отправки и редактирования сообщений в Telegram
- **Event_Model**: Модель данных события, хранящая информацию о связанном сообщении

## Requirements

### Requirement 1: Сохранение идентификатора сообщения о событии

**User Story:** Как система, я хочу сохранять идентификатор сообщения о событии, чтобы иметь возможность обновлять это сообщение при изменении события.

#### Acceptance Criteria

1. WHEN система создаёт новое событие и отправляет сообщение о нём THEN система SHALL сохранить messageId в модели события
2. WHEN система отправляет сообщение о событии THEN система SHALL получить messageId из ответа Telegram API
3. WHEN событие уже имеет сохранённый messageId THEN система SHALL использовать этот messageId для обновления сообщения
4. WHEN событие не имеет сохранённого messageId THEN система SHALL отправить новое сообщение и сохранить полученный messageId
5. WHEN система обновляет событие THEN система SHALL сохранить изменения messageId в базе данных

### Requirement 2: Обновление сообщения при редактировании события

**User Story:** Как пользователь, я хочу, чтобы при редактировании события бот обновлял существующее сообщение, чтобы чат не засорялся множеством сообщений.

#### Acceptance Criteria

1. WHEN пользователь изменяет название события THEN система SHALL обновить существующее сообщение с новым названием
2. WHEN пользователь изменяет дату события THEN система SHALL обновить существующее сообщение с новой датой
3. WHEN пользователь изменяет время события THEN система SHALL обновить существующее сообщение с новым временем
4. WHEN пользователь изменяет описание события THEN система SHALL обновить существующее сообщение с новым описанием
5. WHEN пользователь изменяет любое поле события THEN система SHALL использовать метод editMessageText вместо sendMessage

### Requirement 3: Обновление клавиатуры при редактировании события

**User Story:** Как пользователь, я хочу, чтобы кнопки под сообщением о событии оставались актуальными после редактирования, чтобы я мог продолжать взаимодействовать с событием.

#### Acceptance Criteria

1. WHEN система обновляет сообщение о событии THEN система SHALL обновить inline-клавиатуру с актуальными кнопками
2. WHEN событие имеет статус DRAFT THEN система SHALL отобразить кнопки для редактирования и сохранения
3. WHEN событие имеет статус ACTIVE THEN система SHALL отобразить кнопки для просмотра и управления событием
4. WHEN событие имеет статус COMPLETED THEN система SHALL отобразить кнопки для просмотра завершённого события
5. WHEN система обновляет клавиатуру THEN система SHALL сохранить callback_data для всех кнопок

### Requirement 4: Обработка ошибок при редактировании сообщений

**User Story:** Как пользователь, я хочу получать понятные сообщения об ошибках, если обновление сообщения не удалось, чтобы понимать, что произошло.

#### Acceptance Criteria

1. WHEN сообщение было удалено пользователем THEN система SHALL отправить новое сообщение и сохранить новый messageId
2. WHEN сообщение слишком старое для редактирования THEN система SHALL отправить новое сообщение и сохранить новый messageId
3. WHEN Telegram API возвращает ошибку при редактировании THEN система SHALL обработать ошибку и попытаться отправить новое сообщение
4. WHEN происходит ошибка при редактировании THEN система SHALL записать детали ошибки в лог
5. WHEN система отправляет новое сообщение после ошибки редактирования THEN система SHALL обновить messageId в базе данных

### Requirement 5: Сохранение истории изменений

**User Story:** Как разработчик, я хочу видеть логи изменений сообщений о событиях, чтобы отслеживать работу системы и диагностировать проблемы.

#### Acceptance Criteria

1. WHEN система обновляет сообщение о событии THEN система SHALL записать в лог информацию о событии и messageId
2. WHEN система успешно обновляет сообщение THEN система SHALL записать в лог подтверждение с уровнем INFO
3. WHEN происходит ошибка при обновлении THEN система SHALL записать в лог детали ошибки с уровнем ERROR
4. WHEN система отправляет новое сообщение вместо редактирования THEN система SHALL записать в лог причину и новый messageId
5. WHEN система сохраняет messageId в базу данных THEN система SHALL записать в лог подтверждение операции

### Requirement 6: Миграция базы данных для хранения messageId

**User Story:** Как система, я хочу иметь поле для хранения messageId в таблице событий, чтобы отслеживать связь между событиями и сообщениями.

#### Acceptance Criteria

1. WHEN выполняется миграция базы данных THEN система SHALL добавить поле message_id типа BIGINT в таблицу events
2. WHEN поле message_id добавлено THEN система SHALL разрешить NULL значения для существующих записей
3. WHEN создаётся новое событие THEN система SHALL иметь возможность сохранить messageId
4. WHEN обновляется событие THEN система SHALL иметь возможность обновить messageId
5. WHEN выполняется откат миграции THEN система SHALL удалить поле message_id из таблицы events

### Requirement 7: Обновление модели Event

**User Story:** Как разработчик, я хочу иметь поле messageId в модели Event, чтобы работать с идентификатором сообщения в коде.

#### Acceptance Criteria

1. WHEN определяется модель Event THEN система SHALL включить поле messageId типа Long
2. WHEN поле messageId определено THEN система SHALL разрешить NULL значения
3. WHEN создаётся новый объект Event THEN система SHALL иметь возможность установить messageId
4. WHEN обновляется объект Event THEN система SHALL иметь возможность изменить messageId
5. WHEN сохраняется объект Event THEN система SHALL сохранить messageId в базу данных
