# Документ дизайна

## Обзор

Данный документ описывает дизайн решения для исправления форматирования текста в Telegram-боте семейного календаря. Проблема заключается в том, что все сообщения бота отображаются без форматирования - символы Markdown (*_) отображаются как обычный текст вместо применения стилей.

Корневая причина: в `TelegramMessageService` при создании объектов `SendMessage` не устанавливается параметр `parseMode`, поэтому Telegram API не применяет форматирование к тексту сообщений.

Решение включает:
1. Создание утилитного класса `MarkdownFormatter` для централизованного форматирования и экранирования
2. Обновление `TelegramMessageService` для установки `parseMode="MarkdownV2"` во всех методах отправки
3. Рефакторинг всех обработчиков команд и планировщиков для использования нового форматирования
4. Добавление тестов для проверки корректности форматирования

## Компоненты и интерфейсы

### 1. MarkdownFormatter (Новый утилитный класс)

Утилитный класс для форматирования текста в MarkdownV2 формате Telegram.

```java
package ru.golubyatnikov.family.calendar.bot.util;

/**
 * Утилитный класс для форматирования текста в MarkdownV2 формате Telegram.
 * 
 * <p>MarkdownV2 требует экранирования специальных символов: 
 * _ * [ ] ( ) ~ ` > # + - = | { } . !</p>
 */
public final class MarkdownFormatter {
    
    private MarkdownFormatter() {
        throw new UnsupportedOperationException("Utility class");
    }
    
    /**
     * Экранирует специальные символы MarkdownV2.
     * 
     * @param text текст для экранирования
     * @return экранированный текст
     */
    public static String escape(String text);
    
    /**
     * Форматирует текст жирным шрифтом.
     * 
     * @param text текст для форматирования
     * @return текст в формате *текст*
     */
    public static String bold(String text);
    
    /**
     * Форматирует текст курсивом.
     * 
     * @param text текст для форматирования
     * @return текст в формате _текст_
     */
    public static String italic(String text);
    
    /**
     * Форматирует текст моноширинным шрифтом.
     * 
     * @param text текст для форматирования
     * @return текст в формате `текст`
     */
    public static String code(String text);
    
    /**
     * Форматирует текст жирным курсивом.
     * 
     * @param text текст для форматирования
     * @return текст в формате *_текст_*
     */
    public static String boldItalic(String text);
}
```

**Ключевые особенности:**
- Все методы статические для удобства использования
- Автоматическое экранирование специальных символов внутри форматируемого текста
- Обработка null и пустых строк
- Поддержка всех основных стилей MarkdownV2

### 2. TelegramMessageService (Обновление)

Обновление существующего сервиса для поддержки MarkdownV2.

**Изменения:**

```java
// Было:
SendMessage message = SendMessage.builder()
    .chatId(telegramId.toString())
    .text(text)
    .build();

// Стало:
SendMessage message = SendMessage.builder()
    .chatId(telegramId.toString())
    .text(text)
    .parseMode("MarkdownV2")  // ДОБАВЛЕНО
    .build();
```

**Методы для обновления:**
- `sendMessage(Long telegramId, String text)`
- `sendMessage(Long telegramId, String text, InlineKeyboardMarkup replyMarkup)`
- `sendMessage(Long telegramId, String text, ReplyKeyboardMarkup keyboard)`
- `editMessageText(Long chatId, Integer messageId, String newText, InlineKeyboardMarkup replyMarkup)`

**Обработка ошибок:**
- Добавить логирование текста сообщения при ошибке парсинга (400 Bad Request)
- Это поможет отлаживать проблемы с экранированием

### 3. Обновление обработчиков команд

Все обработчики команд должны использовать `MarkdownFormatter` вместо собственных методов экранирования.

**Обработчики для обновления:**
- `StartCommandHandler` - приветственное сообщение
- `TodayCommandHandler` - список событий на сегодня
- `WeekCommandHandler` - список событий на неделю
- `SearchCommandHandler` - результаты поиска
- `FilterCommandHandler` - отфильтрованные события
- `StatsCommandHandler` - статистика
- `TrashCommandHandler` - корзина
- `MyEventsCommandHandler` - мои события
- `UpcomingEventsCommandHandler` - предстоящие события
- `HelpCommandHandler` - справка

**Пример рефакторинга TodayCommandHandler:**

```java
// Было:
private String escapeMarkdown(String text) {
    if (text == null) return "";
    return text.replace("_", "\\_")
               .replace("*", "\\*")
               // ... остальные символы
}

// Стало:
import static ru.golubyatnikov.family.calendar.bot.util.MarkdownFormatter.*;

private String formatEvent(Event event, User user) {
    StringBuilder sb = new StringBuilder();
    
    // Иконка типа события
    sb.append(event.getIsPersonal() ? "🔒 " : "👨‍👩‍👧‍👦 ");
    
    // Время события
    if (event.getEventTime() != null) {
        sb.append(bold(event.getEventTime().format(TIME_FORMATTER)));
        if (event.getEndTime() != null) {
            sb.append(" - ").append(bold(event.getEndTime().format(TIME_FORMATTER)));
        }
        sb.append(" | ");
    }
    
    // Название события
    sb.append(bold(event.getTitle()));
    
    // Описание события
    if (event.getDescription() != null && !event.getDescription().isBlank()) {
        sb.append("\n   ").append(italic(event.getDescription()));
    }
    
    return sb.toString();
}
```

## Свойства корректности

*Свойство - это характеристика или поведение, которое должно выполняться во всех допустимых выполнениях системы - по сути, формальное утверждение о том, что система должна делать. Свойства служат мостом между спецификациями, читаемыми человеком, и гарантиями корректности, проверяемыми машиной.*

### Свойство 1: Все сообщения используют MarkdownV2

*Для любого* вызова метода `sendMessage` или `editMessageText` в `TelegramMessageService`, объект `SendMessage` или `EditMessageText` должен иметь `parseMode="MarkdownV2"`.

**Проверяет: Требования 1.1, 10.1**

### Свойство 2: Экранирование специальных символов

*Для любого* текста, содержащего специальные символы MarkdownV2 (`_`, `*`, `[`, `]`, `(`, `)`, `~`, `` ` ``, `>`, `#`, `+`, `-`, `=`, `|`, `{`, `}`, `.`, `!`), метод `escape()` должен добавить обратный слеш перед каждым символом.

**Проверяет: Требования 2.1, 2.2**

### Свойство 3: Форматирование жирного текста

*Для любого* текста, переданного в метод `bold()`, результат должен быть обернут в символы `*` и все специальные символы внутри текста должны быть экранированы.

**Проверяет: Требования 9.1**

### Свойство 4: Форматирование курсива

*Для любого* текста, переданного в метод `italic()`, результат должен быть обернут в символы `_` и все специальные символы внутри текста должны быть экранированы.

**Проверяет: Требования 9.2**

### Свойство 5: Форматирование моноширинного текста

*Для любого* текста, переданного в метод `code()`, результат должен быть обернут в символы `` ` `` и все специальные символы внутри текста должны быть экранированы.

**Проверяет: Требования 9.3**

### Свойство 6: Обработка null и пустых строк

*Для любого* метода форматирования (`escape`, `bold`, `italic`, `code`), при передаче null или пустой строки, метод должен вернуть пустую строку без ошибок.

**Проверяет: Требования 2.5**

### Свойство 7: Сохранение переносов строк

*Для любого* текста с переносами строк (`\n`), после применения форматирования переносы строк должны сохраниться в том же количестве и в тех же позициях.

**Проверяет: Требования 14.1, 14.2**

### Свойство 8: Эмодзи не экранируются

*Для любого* текста, содержащего эмодзи (Unicode символы из диапазонов эмодзи), метод `escape()` не должен изменять эмодзи.

**Проверяет: Требования 3.4**

## Обработка ошибок

### 1. Ошибки парсинга MarkdownV2

**Проблема:** Telegram API возвращает 400 Bad Request, если текст содержит неправильно экранированные символы.

**Решение:**
- Добавить детальное логирование текста сообщения при ошибке 400
- Логировать первые 200 символов текста для отладки
- Добавить предупреждение в логи о необходимости проверки экранирования

```java
private void handleTelegramApiError(TelegramApiRequestException e, Long telegramId, String text) {
    Integer errorCode = e.getErrorCode();
    
    if (errorCode == 400) {
        log.error("Bad Request (400): Ошибка парсинга Markdown. " +
                 "telegramId={}, textPreview={}, response={}", 
                 telegramId, 
                 text != null ? text.substring(0, Math.min(200, text.length())) : "null",
                 e.getApiResponse());
    }
    // ... остальная обработка
}
```

### 2. Null и пустые значения

**Проблема:** Методы форматирования могут получить null или пустые строки.

**Решение:**
- Все методы `MarkdownFormatter` должны проверять входные данные
- Возвращать пустую строку для null или пустых входных данных
- Не выбрасывать исключения

```java
public static String escape(String text) {
    if (text == null || text.isEmpty()) {
        return "";
    }
    // ... экранирование
}
```

### 3. Очень длинные сообщения

**Проблема:** Telegram ограничивает длину сообщения 4096 символами.

**Решение:**
- Существующая проверка в `TelegramMessageService.validateSendMessageParams()` уже логирует предупреждение
- Telegram API автоматически обрежет или вернет ошибку
- Дополнительная обработка не требуется на данном этапе

### 4. Двойное экранирование

**Проблема:** Если текст уже содержит экранированные символы, повторное экранирование сломает форматирование.

**Решение:**
- Методы форматирования (`bold`, `italic`, `code`) должны принимать неэкранированный текст
- Экранирование выполняется внутри методов форматирования
- Документировать это поведение в Javadoc

### Обратная совместимость

Изменения не влияют на обратную совместимость:
- API бота не меняется
- Команды остаются теми же
- Структура сообщений остается той же
- Меняется только визуальное отображение текста

### Риски

1. **Неправильное экранирование**
   - Риск: Telegram API вернет ошибку 400
   - Митигация: Тщательное тестирование, детальное логирование

2. **Регрессия в существующих обработчиках**
   - Риск: Сломается форматирование в некоторых командах
   - Митигация: Unit тесты для всех обработчиков

3. **Производительность**
   - Риск: Дополнительное экранирование может замедлить отправку
   - Митигация: Экранирование - быстрая операция, влияние минимально

## Альтернативные решения

### Альтернатива 1: Использование HTML вместо MarkdownV2

**Плюсы:**
- HTML проще в экранировании (только `<`, `>`, `&`)
- Меньше специальных символов для экранирования

**Минусы:**
- Менее читаемый код (теги вместо символов)
- Требует изменения всех существующих сообщений
- MarkdownV2 более естественен для текстовых сообщений

**Решение:** Остаемся с MarkdownV2, так как он уже частично используется в коде.

### Альтернатива 2: Отказ от форматирования

**Плюсы:**
- Не требует экранирования
- Проще в реализации

**Минусы:**
- Сообщения менее читаемы
- Хуже UX
- Не решает текущую проблему

**Решение:** Отклонено, форматирование критично для UX.

## Производительность

### Оценка влияния

- Экранирование символов - O(n) операция, где n - длина текста
- Средняя длина сообщения: 200-500 символов
- Время экранирования: < 1 мс
- Влияние на общее время отправки: < 1%

### Оптимизации

На данном этапе оптимизации не требуются. Если в будущем возникнут проблемы с производительностью:
- Кэширование часто используемых форматированных строк
- Использование StringBuilder вместо String.replace()

## Мониторинг и метрики

### Метрики для отслеживания

1. **Количество ошибок 400 Bad Request**
   - Индикатор проблем с экранированием
   - Должно быть 0 после внедрения

2. **Время отправки сообщений**
   - Проверка, что форматирование не замедляет отправку
   - Должно остаться на том же уровне

3. **Количество успешных отправок**
   - Проверка, что изменения не сломали отправку
   - Должно остаться на том же уровне

### Логирование

- Логировать текст сообщения при ошибке 400 (уже добавлено в дизайн)
- Логировать использование методов форматирования на уровне DEBUG (опционально)
