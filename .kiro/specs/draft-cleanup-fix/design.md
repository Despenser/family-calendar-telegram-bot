# Документ проектирования: Исправление утечки черновиков событий

## Обзор

Проблема заключается в том, что при создании события через текстовый парсинг метод `handleConfirmTextEvent` в `UpdateProcessor` создает черновик через `startEventCreation`, а затем последовательно обновляет его поля. Если на любом из этих шагов возникает ошибка, черновик остается в базе данных с NULL значениями, что нарушает работу системы.

Решение включает три компонента:
1. **Транзакционная обработка** - обернуть весь процесс создания события в транзакцию с откатом при ошибке
2. **Очистка при ошибках** - явно удалять черновики в блоках catch
3. **Периодическая очистка** - автоматически удалять осиротевшие черновики

## Архитектура

### Текущая архитектура (проблемная)

```
UpdateProcessor.handleConfirmTextEvent()
  ├─> conversationService.startEventCreation()      // Создает черновик
  ├─> conversationService.updateEventDate()         // Может упасть
  ├─> conversationService.updateEventTime()         // Может упасть
  ├─> conversationService.updateEventTitle()        // Может упасть
  └─> conversationService.completeEventCreation()   // Может упасть
  
  catch (Exception) {
    // Черновик остается в БД! ❌
  }
```

### Новая архитектура (исправленная)

```
UpdateProcessor.handleConfirmTextEvent()
  @Transactional  // Вся операция в одной транзакции
  ├─> conversationService.startEventCreation()
  ├─> conversationService.updateEventDate()
  ├─> conversationService.updateEventTime()
  ├─> conversationService.updateEventTitle()
  └─> conversationService.completeEventCreation()
  
  catch (Exception) {
    conversationService.cancelEventCreation(userId)  // Явная очистка
    // + автоматический откат транзакции
  }
```

## Компоненты и интерфейсы

### 1. UpdateProcessor

**Изменения:**
- Добавить `@Transactional` к методу `handleConfirmTextEvent`
- Добавить вызов `conversationService.cancelEventCreation(userId)` в блок catch
- Обеспечить откат транзакции при любой ошибке

### 2. ConversationService

**Изменения:**
- Метод `cancelEventCreation` должен быть публичным и безопасным (не падать, если черновиков нет)
- Добавить метод `hasActiveDraft(userId)` для проверки наличия черновика перед очисткой

### 3. DraftCleanupService (новый компонент)

**Назначение:** Периодическая очистка осиротевших черновиков

**Методы:**
- `cleanupOrphanedDrafts()` - удаляет черновики старше 24 часов
- `cleanupOrphanedDraftsOnStartup()` - удаляет черновики старше 1 часа при запуске
- `isOrphanedDraft(Event)` - проверяет, является ли черновик осиротевшим

**Критерии осиротевшего черновика:**
- Статус = DRAFT
- title = NULL
- eventDate = NULL  
- eventTime = NULL
- createdAt старше порогового значения

### 4. AddEventCommandHandler

**Изменения:**
- Добавить обработку ошибок с очисткой черновика
- Обеспечить транзакционность операций

## Модели данных

Изменений в моделях данных не требуется. Используется существующая модель `Event` с полем `createdAt` для определения возраста черновика.

## Свойства корректности

*Свойство - это характеристика или поведение, которое должно выполняться во всех допустимых выполнениях системы - по сути, формальное утверждение о том, что система должна делать. Свойства служат мостом между человекочитаемыми спецификациями и машинно-проверяемыми гарантиями корректности.*


### Свойство 1: Атомарность создания события с очисткой при ошибке

*Для любого* процесса создания события (через текст или команду), если на любом этапе возникает ошибка, то черновик не должен оставаться в базе данных.

**Проверяет: Требования 1.1, 1.2, 1.5, 2.2, 2.4**

### Свойство 2: Полная очистка черновиков при отмене

*Для любого* пользователя, когда он отменяет создание события, все его черновики должны быть удалены из базы данных.

**Проверяет: Требование 1.3**

### Свойство 3: Идентификация и удаление осиротевших черновиков

*Для любого* черновика со статусом DRAFT, если все обязательные поля (title, eventDate, eventTime) равны NULL и черновик старше порогового времени, то система должна идентифицировать его как осиротевший и удалить.

**Проверяет: Требования 1.4, 3.2, 3.4**

## Обработка ошибок

### Стратегия обработки ошибок

1. **Транзакционный откат**: Все операции создания события выполняются в транзакции с автоматическим откатом при ошибке
2. **Явная очистка**: В блоках catch явно вызывается `cancelEventCreation` для гарантированного удаления черновика
3. **Логирование**: Все ошибки логируются с указанием userId и деталей ошибки
4. **Пользовательская обратная связь**: Пользователь получает понятное сообщение об ошибке

### Типы ошибок

1. **Ошибки валидации**: Некорректные данные события (обрабатываются до создания черновика)
2. **Ошибки БД**: Проблемы с сохранением (откат транзакции + очистка)
3. **Ошибки Telegram API**: Проблемы с отправкой сообщений (очистка черновика)
4. **Неожиданные исключения**: Любые другие ошибки (откат + очистка + логирование)

## Стратегия тестирования

### Unit-тесты

1. **ConversationService**:
   - Тест на создание и удаление черновика
   - Тест на безопасность `cancelEventCreation` (не падает, если черновиков нет)
   - Тест на проверку наличия активного черновика

2. **DraftCleanupService**:
   - Тест на идентификацию осиротевших черновиков
   - Тест на удаление черновиков по возрасту
   - Тест на логирование удаленных черновиков

3. **UpdateProcessor**:
   - Тест на откат транзакции при ошибке в `handleConfirmTextEvent`
   - Тест на вызов `cancelEventCreation` в блоке catch

### Property-Based тесты

Для property-based тестирования будем использовать **jqwik** - библиотеку для Java, которая поддерживает генерацию случайных данных и проверку свойств.

**Конфигурация**: Каждый property-based тест должен выполнять минимум 100 итераций для обеспечения достаточного покрытия.

**Свойства для тестирования**:

1. **Свойство 1**: Для любого набора данных события и любой точки отказа в процессе создания, черновик не должен оставаться в БД
2. **Свойство 2**: Для любого пользователя с любым количеством черновиков, отмена должна удалить все черновики
3. **Свойство 3**: Для любого черновика с NULL полями и любого возраста старше порога, он должен быть идентифицирован как осиротевший

### Интеграционные тесты

1. **Полный цикл создания события из текста** с симуляцией ошибок на разных этапах
2. **Полный цикл создания события через команду** с симуляцией ошибок
3. **Тест периодической очистки** с реальной БД и черновиками разного возраста
4. **Тест очистки при запуске** приложения

## Миграция и развертывание

### Шаги развертывания

1. **Добавить DraftCleanupService** с периодической задачей
2. **Обновить UpdateProcessor** с транзакционностью и обработкой ошибок
3. **Обновить AddEventCommandHandler** с обработкой ошибок
4. **Запустить одноразовую очистку** существующих осиротевших черновиков
5. **Мониторинг** логов на предмет ошибок создания событий

### Откат изменений

Если после развертывания возникнут проблемы:
1. Отключить периодическую очистку через конфигурацию
2. Откатить изменения в UpdateProcessor и AddEventCommandHandler
3. Вручную очистить проблемные черновики через SQL

### Мониторинг

Метрики для отслеживания:
- Количество удаленных осиротевших черновиков за период
- Частота ошибок при создании событий
- Количество активных черновиков в системе
- Время жизни черновиков до завершения или отмены
