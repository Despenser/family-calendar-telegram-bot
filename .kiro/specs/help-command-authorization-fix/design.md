# Документ проектирования

## Обзор

Данный документ описывает проектирование исправления логики определения авторизации в команде `/help` Telegram бота семейного календаря. Текущая реализация некорректно определяет статус авторизации пользователя, проверяя только наличие записи в базе данных (`user != null`), но не проверяя принадлежность пользователя к семье.

Исправление включает:
1. Изменение логики проверки авторизации с использованием метода `user.hasFamily()`
2. Добавление тематических эмодзи для команд авторизованных пользователей
3. Сохранение эмодзи замка для неавторизованных пользователей

## Архитектура

### Текущая архитектура

```
HelpCommandHandler
├── handle(Message, User)
│   ├── isAuthorized = (user != null)  ← ПРОБЛЕМА: неправильная проверка
│   ├── buildCommandsList(isAuthorized)
│   └── buildHelpMessage(commandsList, isAuthorized)
└── buildCommandsList(boolean)
    └── Добавляет 🔒 для команд с requiresAuth() если !isAuthorized
```

### Новая архитектура

```
HelpCommandHandler
├── handle(Message, User)
│   ├── isAuthorized = (user != null && user.hasFamily())  ← ИСПРАВЛЕНО
│   ├── buildCommandsList(isAuthorized)
│   └── buildHelpMessage(commandsList, isAuthorized)
├── buildCommandsList(boolean)
│   ├── Если !isAuthorized: добавляет 🔒 для команд с requiresAuth()
│   └── Если isAuthorized: добавляет тематические эмодзи для всех команд
└── getCommandEmoji(String command)  ← НОВЫЙ МЕТОД
    └── Возвращает тематический эмодзи для команды
```

## Компоненты и интерфейсы

### Изменяемые компоненты

#### HelpCommandHandler

**Изменения в методе `handle`:**
```java
// Было:
boolean isAuthorized = (user != null);

// Стало:
boolean isAuthorized = (user != null && user.hasFamily());
```

**Новый метод `getCommandEmoji`:**
```java
/**
 * Возвращает тематический эмодзи для команды.
 * 
 * @param command имя команды (например, "/add_event")
 * @return эмодзи, соответствующий команде
 */
private String getCommandEmoji(String command)
```

**Изменения в методе `buildCommandsList`:**
- Для неавторизованных пользователей: сохраняется текущая логика с 🔒
- Для авторизованных пользователей: добавляется вызов `getCommandEmoji(command)`

## Модели данных

Изменений в моделях данных не требуется. Используется существующий метод `User.hasFamily()`:

```java
public class User {
    // ...
    
    /**
     * Проверяет, является ли пользователь членом какой-либо семьи.
     * 
     * @return true, если пользователь принадлежит семье, иначе false
     */
    public boolean hasFamily() {
        return family != null;
    }
}
```

## Свойства корректности

*Свойство - это характеристика или поведение, которое должно выполняться для всех допустимых выполнений системы - по сути, формальное утверждение о том, что система должна делать. Свойства служат мостом между человекочитаемыми спецификациями и машинно-проверяемыми гарантиями корректности.*

### Свойство 1: Корректное определение авторизации

*Для любого* пользователя, если пользователь существует в базе данных И состоит в семье, то система должна считать его авторизованным; если пользователь не существует ИЛИ не состоит в семье, то система должна считать его неавторизованным.

**Проверяет: Требования 1.1, 1.2, 1.3, 1.4**

### Свойство 2: Отображение эмодзи замка для неавторизованных

*Для любого* неавторизованного пользователя и любой команды, требующей авторизации, система должна отображать эмодзи замка (🔒) перед командой.

**Проверяет: Требования 2.3**

### Свойство 3: Отображение тематических эмодзи для авторизованных

*Для любого* авторизованного пользователя и любой команды, система должна отображать тематический эмодзи (не замок) перед командой.

**Проверяет: Требования 2.4, 3.1, 3.2, 3.3, 3.4, 3.5**

### Свойство 4: Согласованность логики авторизации

*Для любого* пользователя, логика определения авторизации в HelpCommandHandler должна быть идентична логике в других обработчиках команд (использование `user != null && user.hasFamily()`).

**Проверяет: Требования 4.1, 4.2**

### Свойство 5: Корректное логирование статуса

*Для любого* пользователя, логи должны корректно отражать фактический статус авторизации (основанный на `user.hasFamily()`), а не только на наличии записи в БД.

**Проверяет: Требования 4.3**

## Обработка ошибок

### Существующая обработка ошибок

HelpCommandHandler уже имеет обработку следующих ошибок:
- `IllegalArgumentException` при `message == null`
- Проверка на пустой список обработчиков команд
- Фильтрация `null` значений в списке обработчиков

### Дополнительная обработка

Дополнительной обработки ошибок не требуется, так как:
- Метод `user.hasFamily()` безопасен и не выбрасывает исключений
- Проверка `user != null` выполняется перед вызовом `user.hasFamily()`
- Метод `getCommandEmoji()` всегда возвращает валидное значение (по умолчанию пустую строку)

## Стратегия тестирования

### Unit-тесты

Необходимо создать или обновить следующие unit-тесты:

1. **Тест проверки авторизации для пользователя с семьей**
   - Создать пользователя с семьей
   - Вызвать `handle()`
   - Проверить, что `isAuthorized = true`
   - Проверить отсутствие эмодзи замка в ответе
   - Проверить наличие тематических эмодзи

2. **Тест проверки авторизации для пользователя без семьи**
   - Создать пользователя без семьи (`family = null`)
   - Вызвать `handle()`
   - Проверить, что `isAuthorized = false`
   - Проверить наличие эмодзи замка для команд с `requiresAuth() = true`
   - Проверить наличие информации о регистрации в ответе

3. **Тест проверки авторизации для null пользователя**
   - Передать `user = null`
   - Вызвать `handle()`
   - Проверить, что `isAuthorized = false`
   - Проверить наличие эмодзи замка для команд с `requiresAuth() = true`

4. **Тест маппинга эмодзи для всех команд**
   - Для каждой команды проверить, что `getCommandEmoji()` возвращает корректный эмодзи
   - Проверить, что для неизвестной команды возвращается пустая строка

5. **Тест формирования списка команд для авторизованного пользователя**
   - Создать пользователя с семьей
   - Вызвать `buildCommandsList(true)`
   - Проверить, что все команды имеют тематические эмодзи
   - Проверить отсутствие эмодзи замка

6. **Тест формирования списка команд для неавторизованного пользователя**
   - Вызвать `buildCommandsList(false)`
   - Проверить, что команды с `requiresAuth() = true` имеют эмодзи замка
   - Проверить, что команды с `requiresAuth() = false` не имеют эмодзи замка

### Property-Based тесты

Property-based тесты не требуются для данной функции, так как:
- Логика детерминирована и не зависит от случайных входных данных
- Количество команд фиксировано
- Маппинг эмодзи статичен
- Unit-тесты полностью покрывают все возможные сценарии

### Интеграционные тесты

Интеграционные тесты не требуются, так как:
- Изменения локализованы в одном классе
- Нет взаимодействия с внешними системами
- Нет изменений в базе данных
- Unit-тесты достаточны для проверки корректности

## Влияние на производительность

Изменения не окажут заметного влияния на производительность:
- Добавляется один дополнительный вызов метода `user.hasFamily()` (O(1))
- Метод `getCommandEmoji()` выполняет простой switch/if-else (O(1))
- Количество команд фиксировано и невелико (~10-15)
- Общая сложность остается O(n), где n - количество команд

## Обратная совместимость

Изменения полностью обратно совместимы:
- Публичный API `HelpCommandHandler` не изменяется
- Интерфейс `CommandHandler` не изменяется
- Формат ответа остается совместимым с Telegram MarkdownV2
- Существующие тесты могут потребовать обновления, но не ломаются

## Альтернативные решения

### Альтернатива 1: Создание отдельного метода isUserAuthorized()

**Описание:** Вынести логику проверки авторизации в отдельный метод `isUserAuthorized(User user)`.

**Преимущества:**
- Более явная семантика
- Легче тестировать изолированно
- Можно переиспользовать в других местах

**Недостатки:**
- Избыточность для простой проверки
- Дополнительный метод в классе

**Решение:** Не выбрано, так как проверка достаточно проста и используется только в одном месте.

### Альтернатива 2: Хранение маппинга эмодзи в конфигурации

**Описание:** Вынести маппинг команд на эмодзи в `application.yml` или отдельный конфигурационный файл.

**Преимущества:**
- Легче изменять эмодзи без перекомпиляции
- Централизованная конфигурация

**Недостатки:**
- Усложнение архитектуры
- Дополнительный слой абстракции
- Маппинг вряд ли будет часто меняться

**Решение:** Не выбрано, так как маппинг статичен и не требует частых изменений.

### Альтернатива 3: Использование аннотаций для эмодзи

**Описание:** Добавить аннотацию `@CommandEmoji("📅")` к каждому обработчику команд.

**Преимущества:**
- Декларативный подход
- Эмодзи определяется рядом с командой
- Автоматическое извлечение через рефлексию

**Недостатки:**
- Требует изменений во всех обработчиках
- Использование рефлексии
- Усложнение кода

**Решение:** Не выбрано, так как требует изменений во многих файлах и усложняет архитектуру.

## План развертывания

1. Внести изменения в `HelpCommandHandler.java`
2. Запустить unit-тесты
3. Исправить failing тесты (если есть)
4. Выполнить ручное тестирование:
   - Протестировать с пользователем без семьи
   - Протестировать с пользователем с семьей
   - Протестировать с незарегистрированным пользователем
5. Задеплоить изменения
6. Мониторить логи на наличие ошибок
