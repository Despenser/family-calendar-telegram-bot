# Документ требований

## Введение

Данная спецификация описывает улучшение обработки неавторизованных пользователей в семейном календарь-боте. В настоящее время команды, требующие авторизации, молча отклоняют запросы от незарегистрированных пользователей без информативных сообщений. Система должна предоставлять понятные и дружелюбные сообщения о необходимости регистрации, объясняя пользователю, как получить доступ к функционалу бота.

## Глоссарий

- **Система**: Существующее Spring Boot приложение семейного календарь-бота
- **Авторизованный пользователь**: Пользователь, зарегистрированный в системе и имеющий запись в таблице users
- **Неавторизованный пользователь**: Пользователь, не зарегистрированный в системе
- **Команда с авторизацией**: Команда бота, требующая наличия зарегистрированного пользователя
- **TelegramId**: Уникальный идентификатор пользователя в Telegram
- **CommandHandler**: Обработчик команды бота
- **UserService**: Сервис для работы с пользователями
- **TelegramMessageService**: Сервис для отправки сообщений через Telegram Bot API

## Требования

### Требование 1

**Пользовательская история:** Как незарегистрированный пользователь, я хочу получать понятное сообщение при попытке использовать команды бота, чтобы понимать, почему функционал недоступен и что нужно сделать.

#### Критерии приемки

1. WHEN незарегистрированный пользователь отправляет команду, требующую авторизации, THEN Система ДОЛЖНА проверить наличие пользователя в базе данных по Telegram ID
2. WHEN пользователь не найден в базе данных, THEN Система ДОЛЖНА отправить информативное сообщение о необходимости регистрации
3. WHEN сообщение формируется, THEN Система ДОЛЖНА включать эмодзи "🔒" для визуального обозначения ограничения доступа
4. WHEN сообщение отправляется, THEN Система ДОЛЖНА объяснять, что функционал будет доступен после регистрации в семейном календаре
5. WHEN сообщение содержит инструкции, THEN Система ДОЛЖНА указывать, как пользователь может получить доступ (например, обратиться к администратору семьи)

### Требование 2

**Пользовательская история:** Как разработчик, я хочу иметь централизованный механизм проверки авторизации, чтобы все команды обрабатывали неавторизованных пользователей единообразно.

#### Критерии приемки

1. WHEN создается новый обработчик команды, THEN Система ДОЛЖНА предоставлять переиспользуемый метод проверки авторизации
2. WHEN метод проверки вызывается, THEN Система ДОЛЖНА возвращать Optional с пользователем или пустое значение
3. WHEN пользователь не найден, THEN Система ДОЛЖНА автоматически отправлять стандартное сообщение об отсутствии доступа
4. WHEN обработчик команды использует проверку авторизации, THEN Система ДОЛЖНА позволять прерывать выполнение команды при отсутствии авторизации
5. WHEN метод проверки логирует событие, THEN Система ДОЛЖНА записывать попытку доступа неавторизованного пользователя с уровнем INFO

### Требование 3

**Пользовательская история:** Как незарегистрированный пользователь, я хочу видеть разные сообщения для разных типов команд, чтобы понимать специфику ограничений.

#### Критерии приемки

1. WHEN незарегистрированный пользователь пытается создать событие, THEN Система ДОЛЖНА отправить сообщение: "🔒 Создание событий доступно только зарегистрированным пользователям семейного календаря"
2. WHEN незарегистрированный пользователь пытается просмотреть события, THEN Система ДОЛЖНА отправить сообщение: "🔒 Просмотр событий доступен только членам семейного календаря"
3. WHEN незарегистрированный пользователь пытается редактировать или удалять события, THEN Система ДОЛЖНА отправить сообщение: "🔒 Управление событиями доступно только зарегистрированным пользователям"
4. WHEN незарегистрированный пользователь пытается использовать поиск или фильтры, THEN Система ДОЛЖНА отправить сообщение: "🔒 Поиск и фильтрация событий доступны только членам семейного календаря"
5. WHEN любое сообщение об ограничении отправляется, THEN Система ДОЛЖНА добавлять текст: "Для получения доступа обратитесь к администратору вашей семьи"

### Требование 4

**Пользовательская история:** Как незарегистрированный пользователь, я хочу иметь доступ к базовым информационным командам, чтобы узнать о возможностях бота.

#### Критерии приемки

1. WHEN незарегистрированный пользователь отправляет команду /start, THEN Система ДОЛЖНА отправить приветственное сообщение без требования авторизации
2. WHEN незарегистрированный пользователь отправляет команду /help, THEN Система ДОЛЖНА показать список доступных команд с пометкой о необходимости регистрации
3. WHEN команда /help отображается для незарегистрированного пользователя, THEN Система ДОЛЖНА выделять команды, требующие авторизации, эмодзи "🔒"
4. WHEN незарегистрированный пользователь просматривает помощь, THEN Система ДОЛЖНА включать информацию о процессе регистрации
5. WHEN приветственное сообщение отправляется, THEN Система ДОЛЖНА объяснять назначение бота и как получить доступ к функционалу

### Требование 5

**Пользовательская история:** Как разработчик, я хочу обновить все существующие обработчики команд для поддержки информативных сообщений, чтобы улучшить пользовательский опыт.

#### Критерии приемки

1. WHEN обработчик AddEventCommandHandler проверяет авторизацию, THEN Система ДОЛЖНА отправлять специфичное сообщение о недоступности создания событий
2. WHEN обработчики MyEventsCommandHandler, UpcomingEventsCommandHandler, TodayCommandHandler, WeekCommandHandler проверяют авторизацию, THEN Система ДОЛЖНА отправлять сообщение о недоступности просмотра событий
3. WHEN обработчики SearchCommandHandler, FilterCommandHandler проверяют авторизацию, THEN Система ДОЛЖНА отправлять сообщение о недоступности поиска и фильтрации
4. WHEN обработчик TrashCommandHandler проверяет авторизацию, THEN Система ДОЛЖНА отправлять сообщение о недоступности управления корзиной
5. WHEN обработчик StatsCommandHandler проверяет авторизацию, THEN Система ДОЛЖНА отправлять сообщение о недоступности статистики

### Требование 6

**Пользовательская история:** Как разработчик, я хочу логировать попытки доступа неавторизованных пользователей, чтобы отслеживать интерес к боту и потенциальные проблемы безопасности.

#### Критерии приемки

1. WHEN незарегистрированный пользователь пытается использовать команду с авторизацией, THEN Система ДОЛЖНА логировать событие с уровнем INFO
2. WHEN событие логируется, THEN Система ДОЛЖНА включать telegram_id, username, команду и timestamp
3. WHEN происходит несколько попыток от одного пользователя, THEN Система ДОЛЖНА логировать каждую попытку отдельно
4. WHEN логирование выполняется, THEN Система ДОЛЖНА использовать структурированный формат для удобства анализа
5. WHERE используется production окружение, Система ДОЛЖНА агрегировать статистику попыток доступа для мониторинга

### Требование 7

**Пользовательская история:** Как член семьи, я хочу, чтобы сообщения об ограничении доступа были дружелюбными и мотивирующими, чтобы новые пользователи не чувствовали себя отвергнутыми.

#### Критерии приемки

1. WHEN Система формирует сообщение об ограничении, THEN Система ДОЛЖНА использовать позитивный и приветливый тон
2. WHEN сообщение отправляется, THEN Система ДОЛЖНА подчеркивать преимущества регистрации в семейном календаре
3. WHEN текст сообщения составляется, THEN Система ДОЛЖНА избегать негативных формулировок типа "доступ запрещен" или "вы не можете"
4. WHEN сообщение включает инструкции, THEN Система ДОЛЖНА использовать конструктивные формулировки типа "станет доступно после регистрации"
5. WHEN отправляется информация о регистрации, THEN Система ДОЛЖНА кратко описывать возможности бота для мотивации пользователя

### Требование 8

**Пользовательская история:** Как разработчик, я хочу иметь конфигурируемые сообщения об ограничении доступа, чтобы легко изменять тексты без изменения кода.

#### Критерии приемки

1. WHEN приложение запускается, THEN Система ДОЛЖНА загружать тексты сообщений из конфигурационного файла или базы данных
2. WHEN сообщение формируется, THEN Система ДОЛЖНА использовать шаблоны с подстановкой параметров (например, имени команды)
3. WHEN конфигурация изменяется, THEN Система ДОЛЖНА применять новые тексты без перезапуска приложения
4. WHEN шаблон сообщения не найден, THEN Система ДОЛЖНА использовать дефолтное сообщение с логированием предупреждения
5. WHERE используются разные языки, Система ДОЛЖНА поддерживать локализацию сообщений об ограничении доступа

### Требование 9

**Пользовательская история:** Как разработчик, я хочу иметь unit-тесты для проверки обработки неавторизованных пользователей, чтобы гарантировать корректность работы механизма авторизации.

#### Критерии приемки

1. WHEN создается тест для обработчика команды, THEN Система ДОЛЖНА включать тест-кейс для неавторизованного пользователя
2. WHEN тест выполняется, THEN Система ДОЛЖНА проверять, что отправляется корректное сообщение об ограничении доступа
3. WHEN тест проверяет логирование, THEN Система ДОЛЖНА верифицировать, что попытка доступа залогирована
4. WHEN все тесты выполняются, THEN Система ДОЛЖНА покрывать все обработчики команд с требованием авторизации
