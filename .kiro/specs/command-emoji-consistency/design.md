# Design Document: Добавление эмодзи к командам в сообщениях

## Overview

Данный дизайн описывает подход к добавлению эмодзи к командам в сообщениях пользователю для обеспечения визуальной консистентности. В настоящее время команды /start и /help уже используют эмодзи в своих сообщениях, но в других частях приложения команды отображаются без эмодзи. Это создает визуальную несогласованность.

Решение заключается в систематическом добавлении эмодзи перед командами во всех сообщениях, используя существующий маппинг эмодзи из HelpCommandHandler.

## Architecture

Архитектура решения основана на следующих принципах:

1. **Централизованный маппинг эмодзи**: Используется существующий маппинг `COMMAND_EMOJIS` из `HelpCommandHandler`, который уже содержит все необходимые эмодзи для команд.

2. **Локальные изменения**: Изменения вносятся непосредственно в строковые литералы сообщений в каждом классе. Это минимизирует риск и не требует изменения архитектуры.

3. **Консистентность**: Все эмодзи должны соответствовать маппингу из HelpCommandHandler для обеспечения единообразия во всем приложении.

## Data Models

Изменения в моделях данных не требуются. Все изменения касаются только строковых литералов в сообщениях.

### Property 1: Консистентность эмодзи в сообщениях

### Property 2: Наличие эмодзи перед командами

*For any* сообщение, содержащее команду бота, перед командой должен присутствовать соответствующий эмодзи.

### Property 3: Корректное экранирование команд

**Validates: Requirements 1.1, 1.2, 1.3, 1.4, 2.1, 2.2, 2.3, 2.4, 2.5, 2.6, 3.1, 4.1, 4.2, 4.3, 5.1**

## Error Handling

Изменения не влияют на обработку ошибок. Все существующие механизмы обработки ошибок остаются без изменений.

Потенциальные проблемы:
1. **Неправильное экранирование**: Эмодзи не требуют экранирования в MarkdownV2, но команды должны быть корректно экранированы с помощью `escape()`.
2. **Несоответствие маппингу**: Необходимо убедиться, что используются правильные эмодзи из маппинга HelpCommandHandler.

## Testing Strategy

### Unit Tests

Для данной задачи unit-тесты не требуются, так как изменения касаются только строковых литералов. Существующие тесты должны продолжать проходить без изменений.

### Property-Based Tests

Property-based тесты не требуются для данной задачи, так как:
1. Изменения касаются только статических строковых литералов
2. Нет логики, которую нужно тестировать с различными входными данными
3. Визуальная консистентность проверяется вручную

### Manual Testing

Необходимо вручную проверить следующие сценарии:

1. **CommandDispatcher**:
   - Отправить сообщение без текста
   - Отправить команду без символа "/"
   - Отправить неизвестную команду
   - Попытаться выполнить команду без авторизации

2. **UpdateProcessor**:
   - Вызвать ошибку при создании события
   - Отправить текст в неправильном формате
   - Попытаться отправить файл без авторизации
   - Попытаться прикрепить файл без создания события
   - Отправить команду без символа "/"
   - Отправить неизвестную команду

3. **EventService**:
   - Открыть пустой список "Мои события"

4. **SearchCommandHandler**:
   - Выполнить поиск без результатов
   - Вызвать ошибку при повторном поиске

5. **CallbackQueryDispatcher**:
   - Попытаться выполнить callback query без авторизации

### Integration Tests

Integration тесты не требуются, так как изменения не влияют на взаимодействие между компонентами.

## Implementation Notes

1. Все изменения должны использовать метод `escape()` из `MarkdownFormatter` для корректного экранирования команд.
2. Эмодзи не требуют экранирования и добавляются непосредственно в строку.
3. Формат: `"эмодзи " + escape("/команда")`
4. Необходимо сохранить существующее форматирование и структуру сообщений.
5. Все изменения должны быть минимальными и не затрагивать логику приложения.
