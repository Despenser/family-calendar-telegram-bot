# Design Document

## Overview

Данный документ описывает дизайн исправления ошибок парсинга MarkdownV2, обнаруженных в Docker-логах приложения. Проблема заключается в том, что некоторые части кода используют `String.format` для формирования сообщений вместо специализированного метода `formatMessage` из `MarkdownFormatter`, что приводит к неэкранированным специальным символам и ошибкам при отправке сообщений в Telegram.

## Architecture

### Текущая архитектура

Приложение использует утилитный класс `MarkdownFormatter` для корректного экранирования специальных символов MarkdownV2. Класс предоставляет следующие методы:

- `escape(String text)` - экранирует все специальные символы
- `bold(String text)` - форматирует текст жирным шрифтом с автоматическим экранированием
- `italic(String text)` - форматирует текст курсивом с автоматическим экранированием
- `code(String text)` - форматирует текст моноширинным шрифтом
- `formatMessage(String template, Object... args)` - форматирует сообщение с автоматическим экранированием всех частей

### Проблемные места

Анализ Docker-логов выявил следующие проблемные места:

1. **MyEventsCommandHandler.java** (строки 353-356):
   - Использует `String.format` с неэкранированным статическим текстом
   - Текст содержит точки, которые не экранированы
   - Ошибка: "can't parse entities: Character '.' is reserved and must be escaped"

2. **TrashCommandHandler.java** (строка 86):
   - Использует `italic()` с неэкранированным текстом "Удаленные события хранятся 30 дней"
   - Текст содержит точки и другие специальные символы

### Решение

Заменить все использования `String.format` на `formatMessage` из `MarkdownFormatter` и обернуть статический текст в вызовы `escape()`.

## Components and Interfaces

### Затронутые компоненты

#### 1. MyEventsCommandHandler

**Текущая реализация:**
```java
return String.format("✅ %s\n\n" +
       "Событие успешно удалено из календаря.\n\n" +
       "Используйте %s для просмотра оставшихся событий.",
       bold("Событие удалено"), escape("/my_events"));
```

**Проблема:** Статический текст "Событие успешно удалено из календаря." содержит точки, которые не экранированы.

**Решение:**
```java
return formatMessage("✅ %s\n\n" +
       "Событие успешно удалено из календаря.\n\n" +
       "Используйте %s для просмотра оставшихся событий.",
       bold("Событие удалено"), code("/my_events"));
```

#### 2. TrashCommandHandler

**Текущая реализация:**
```java
messageBuilder.append(formatMessage("🗑️ %s\n\n", bold("Корзина")));
messageBuilder.append(italic("Удаленные события хранятся 30 дней")).append("\n\n");
```

**Проблема:** Текст "Удаленные события хранятся 30 дней" передается в `italic()` без предварительного экранирования.

**Решение:**
```java
messageBuilder.append(formatMessage("🗑️ %s\n\n%s\n\n", 
    bold("Корзина"), 
    italic("Удаленные события хранятся 30 дней")));
```

Или альтернативно:
```java
messageBuilder.append(formatMessage("🗑️ %s\n\n", bold("Корзина")));
messageBuilder.append(formatMessage("%s\n\n", italic("Удаленные события хранятся 30 дней")));
```

## Error Handling

### Существующая обработка ошибок

`TelegramMessageService` уже имеет механизм повторных попыток отправки сообщений:
- 3 попытки отправки с экспоненциальной задержкой
- Логирование ошибок парсинга MarkdownV2
- Возврат информативных сообщений об ошибках

### Дополнительная обработка

После исправления экранирования, ошибки парсинга MarkdownV2 должны исчезнуть. Однако, для предотвращения подобных проблем в будущем, рекомендуется:

1. Добавить валидацию экранирования в unit-тестах
2. Использовать статический анализ кода для обнаружения использования `String.format` с MarkdownV2
3. Документировать best practices по использованию `MarkdownFormatter`

## Testing Strategy

### Unit Tests

Для каждого исправленного метода необходимо создать или обновить unit-тесты:

1. **MyEventsCommandHandlerTest**:
   - Тест на корректное экранирование сообщения об удалении
   - Проверка отсутствия неэкранированных точек
   - Проверка корректного форматирования команды `/my_events`

2. **TrashCommandHandlerTest**:
   - Тест на корректное экранирование заголовка корзины
   - Тест на корректное экранирование текста "Удаленные события хранятся 30 дней"
   - Тест на корректное экранирование дат в формате событий

### Integration Tests

Интеграционные тесты должны проверять:
- Успешную отправку сообщений в mock Telegram API
- Отсутствие ошибок парсинга MarkdownV2
- Корректное отображение форматированного текста

### Manual Testing

После внедрения изменений необходимо провести ручное тестирование:
1. Удалить событие и проверить сообщение
2. Открыть корзину и проверить отображение удаленных событий
3. Проверить логи Docker на отсутствие ошибок парсинга

## Implementation Notes

### Порядок внедрения

1. Исправить `MyEventsCommandHandler` - метод обработки удаления события
2. Исправить `TrashCommandHandler` - метод формирования списка корзины
3. Запустить unit-тесты для проверки корректности
4. Собрать Docker-образ и протестировать в контейнере
5. Проверить логи Docker на отсутствие ошибок

### Потенциальные проблемы

1. **Двойное экранирование**: Необходимо убедиться, что текст не экранируется дважды
2. **Эмодзи**: Эмодзи не должны экранироваться, `MarkdownFormatter` уже учитывает это
3. **Переносы строк**: `\n` не должны экранироваться, они корректно обрабатываются

### Best Practices

1. Всегда использовать `formatMessage` вместо `String.format` для MarkdownV2
2. Оборачивать статический текст в `escape()` если он содержит специальные символы
3. Использовать `code()` для команд (например, `/my_events`)
4. Использовать `bold()` и `italic()` для форматирования, они автоматически экранируют содержимое
