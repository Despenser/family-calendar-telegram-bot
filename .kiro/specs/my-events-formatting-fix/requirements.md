# Требования: Исправление форматирования списка активных событий

## Введение

Данный документ описывает требования к исправлению форматирования вывода списка активных событий в команде `/my_events`. Необходимо привести формат вывода в соответствие с форматом команды `/trash`, где заголовок и первое событие отображаются в одном сообщении.

## Глоссарий

- **System**: Telegram-бот семейного календаря
- **User**: Пользователь бота
- **Active_Event**: Активное (не удаленное) событие в календаре
- **Event_List**: Список активных событий пользователя
- **Header_Message**: Заголовочное сообщение со счетчиком событий
- **Event_Message**: Сообщение с деталями одного события

## Требования

### Требование 1: Объединенный вывод заголовка и первого события

**User Story:** Как пользователь, я хочу видеть заголовок списка событий и первое событие в одном сообщении, чтобы формат был единообразным с корзиной.

#### Критерии приемки

1. WHEN пользователь выполняет команду `/my_events` и у него есть события, THEN THE System SHALL отправить заголовок и первое событие в одном сообщении
2. WHEN пользователь выполняет команду `/my_events` и у него есть более одного события, THEN THE System SHALL отправить остальные события отдельными сообщениями
3. WHEN пользователь выполняет команду `/my_events` и у него нет событий, THEN THE System SHALL отправить только сообщение об отсутствии событий

### Требование 2: Единообразное форматирование

**User Story:** Как пользователь, я хочу, чтобы список активных событий и корзина имели одинаковый формат отображения, чтобы интерфейс был предсказуемым.

#### Критерии приемки

1. WHEN пользователь просматривает список активных событий, THEN THE System SHALL использовать тот же формат заголовка, что и в корзине
2. WHEN пользователь просматривает список активных событий, THEN THE System SHALL отображать заголовок с эмодзи "📋" и текстом "Мои события"
3. WHEN пользователь просматривает список активных событий с более чем одним событием, THEN THE System SHALL отображать информацию "Всего событий: N" в заголовке

### Требование 3: Сохранение функциональности inline-кнопок

**User Story:** Как пользователь, я хочу иметь возможность редактировать и удалять события из списка, чтобы управлять своим календарем.

#### Критерии приемки

1. WHEN пользователь просматривает событие в списке, THEN THE System SHALL отображать inline-кнопки "Редактировать" и "Удалить" под каждым событием
2. WHEN пользователь нажимает кнопку "Редактировать", THEN THE System SHALL инициировать процесс редактирования события
3. WHEN пользователь нажимает кнопку "Удалить", THEN THE System SHALL переместить событие в корзину

### Требование 4: Обработка ошибок форматирования

**User Story:** Как пользователь, я хочу получать события даже при ошибках форматирования, чтобы не терять доступ к своим данным.

#### Критерии приемки

1. WHEN происходит ошибка форматирования MarkdownV2 при отправке события, THEN THE System SHALL использовать fallback механизм отправки без форматирования
2. WHEN используется fallback механизм, THEN THE System SHALL сохранить inline-кнопки для управления событием
3. WHEN происходит ошибка отправки события, THEN THE System SHALL записать ошибку в лог и продолжить отправку остальных событий
