# Проектирование: Исправление форматирования списка активных событий

## Обзор

Данный документ описывает проектное решение для исправления форматирования вывода списка активных событий в команде `/my_events`. Цель - привести формат вывода в соответствие с форматом команды `/trash`, где заголовок и первое событие отображаются в одном сообщении.

## Архитектура

Решение затрагивает только класс `MyEventsCommandHandler` и не требует изменений в других компонентах системы. Основная идея - изменить логику метода `handle()` так, чтобы первое событие отправлялось вместе с заголовком в одном сообщении.

### Текущая реализация

```
1. Формируется заголовок с информацией о количестве событий
2. Заголовок отправляется отдельным сообщением
3. Каждое событие отправляется отдельным сообщением с inline-кнопками
```

### Новая реализация

```
1. Формируется заголовок с информацией о количестве событий
2. Если есть события:
   a. К заголовку добавляется первое событие
   b. Объединенное сообщение отправляется с inline-кнопками первого события
   c. Остальные события отправляются отдельными сообщениями
3. Если событий нет, отправляется только сообщение об отсутствии событий
```

## Компоненты и интерфейсы

### MyEventsCommandHandler

**Изменяемые методы:**

1. `handle(Message message, User user)` - основной метод обработки команды
   - Изменение: логика формирования и отправки первого сообщения
   - Вход: Message, User
   - Выход: String (заголовок для логирования)

**Неизменяемые методы:**

- `formatEvent(Event event)` - форматирование одного события
- `sendWithoutFormatting(Long chatId, Event event)` - fallback механизм
- `buildNoEventsMessage()` - сообщение об отсутствии событий
- Все остальные методы класса

## Модели данных

Изменения в моделях данных не требуются. Используются существующие классы:
- `Event` - модель события
- `User` - модель пользователя
- `Message` - модель сообщения Telegram

## Correctness Properties

*Свойство корректности (property) - это характеристика или поведение, которое должно выполняться во всех допустимых выполнениях системы. По сути, это формальное утверждение о том, что система должна делать. Свойства служат мостом между человекочитаемыми спецификациями и машинно-проверяемыми гарантиями корректности.*

### Property 1: Объединение заголовка и первого события

*For any* непустого списка событий пользователя, первое сообщение должно содержать как заголовок, так и отформатированное первое событие.

**Validates: Requirements 1.1**

### Property 2: Отдельная отправка остальных событий

*For any* списка событий с более чем одним событием, все события после первого должны отправляться отдельными сообщениями.

**Validates: Requirements 1.2**

### Property 3: Сохранение inline-кнопок

*For any* события в списке, сообщение с этим событием должно содержать inline-клавиатуру с кнопками "Редактировать" и "Удалить".

**Validates: Requirements 3.1, 3.2, 3.3**

### Property 4: Fallback при ошибках форматирования

*For any* события, при ошибке форматирования MarkdownV2 система должна отправить событие без форматирования, но с сохранением inline-кнопок.

**Validates: Requirements 4.1, 4.2**

## Обработка ошибок

### Ошибки форматирования MarkdownV2

**Текущий механизм (сохраняется):**
1. При ошибке 400 (Bad Request) от Telegram API
2. Логируется предупреждение
3. Вызывается метод `sendWithoutFormatting()`
4. Событие отправляется без MarkdownV2, но с inline-кнопками

### Ошибки отправки сообщений

**Текущий механизм (сохраняется):**
1. Ошибка логируется
2. Счетчик ошибок увеличивается
3. Обработка продолжается для следующих событий

### Новые сценарии ошибок

**Ошибка при отправке объединенного сообщения:**
1. Если не удается отправить заголовок с первым событием
2. Логируется ошибка
3. Попытка отправить заголовок отдельно
4. Попытка отправить первое событие отдельно с fallback механизмом

## Стратегия тестирования

### Unit-тесты

1. **Тест пустого списка событий**
   - Проверка, что возвращается сообщение об отсутствии событий
   - Проверка, что не отправляются дополнительные сообщения

2. **Тест одного события**
   - Проверка, что заголовок и событие объединены в одно сообщение
   - Проверка наличия inline-кнопок

3. **Тест нескольких событий**
   - Проверка, что первое сообщение содержит заголовок и первое событие
   - Проверка, что остальные события отправлены отдельно
   - Проверка правильного количества отправленных сообщений

4. **Тест fallback механизма**
   - Симуляция ошибки MarkdownV2
   - Проверка вызова метода `sendWithoutFormatting()`
   - Проверка сохранения inline-кнопок

### Property-based тесты

Для данной задачи property-based тесты не требуются, так как:
- Логика не зависит от случайных входных данных
- Поведение детерминировано и зависит только от количества событий
- Unit-тесты полностью покрывают все сценарии

### Интеграционные тесты

1. **Интеграционный тест с реальным TelegramMessageService**
   - Проверка корректной отправки сообщений
   - Проверка формата сообщений
   - Проверка inline-клавиатур

## Детали реализации

### Псевдокод изменений в методе handle()

```
function handle(message, user):
    // Получение событий (без изменений)
    events = eventService.getUserEvents(user.getId())
    
    if events.isEmpty():
        return buildNoEventsMessage()
    
    // Формирование заголовка
    header = buildHeader(events.size())
    
    // Обработка первого события
    firstEvent = events.get(0)
    firstEventText = formatEvent(firstEvent)
    
    // Объединение заголовка и первого события
    combinedMessage = header + "\n" + firstEventText
    keyboard = keyboardService.createEventActionsKeyboard(firstEvent.getId())
    
    try:
        // Отправка объединенного сообщения
        messageService.sendMessageWithInlineKeyboard(chatId, combinedMessage, keyboard)
        successCount++
    catch TelegramApiRequestException(e):
        if e.errorCode == 400:
            // Fallback для первого события
            try:
                messageService.sendMessage(chatId, header)
                sendWithoutFormatting(chatId, firstEvent)
                successCount++
            catch Exception:
                failureCount++
        else:
            failureCount++
    
    // Обработка остальных событий (без изменений)
    for i from 1 to events.size() - 1:
        event = events.get(i)
        // ... существующая логика отправки
    
    return header
```

### Метод buildHeader()

```
private function buildHeader(eventCount):
    header = "📋 " + bold("Мои события") + "\n\n"
    header += escape("Всего событий: ") + escape(String.valueOf(eventCount)) + escape("\n")
    return header
```

## Влияние на производительность

- **Минимальное**: количество отправляемых сообщений уменьшается на 1
- **Положительное**: меньше запросов к Telegram API
- **Пользовательский опыт**: улучшается за счет более компактного отображения

## Обратная совместимость

Изменения полностью обратно совместимы:
- API методов не меняется
- Формат данных не меняется
- Поведение других команд не затрагивается
- Пользователи увидят только улучшенное форматирование

## Альтернативные решения

### Альтернатива 1: Отправка всех событий одним сообщением

**Плюсы:**
- Минимальное количество сообщений

**Минусы:**
- Ограничение Telegram на длину сообщения (4096 символов)
- Сложность с inline-кнопками (ограничение на количество)
- Плохая читаемость при большом количестве событий

**Решение:** Отклонено

### Альтернатива 2: Пагинация событий

**Плюсы:**
- Лучшая организация при большом количестве событий
- Меньше сообщений в чате

**Минусы:**
- Сложность реализации
- Необходимость хранения состояния пагинации
- Избыточно для текущей задачи

**Решение:** Отклонено (может быть рассмотрено в будущем)

### Выбранное решение

Объединение заголовка с первым событием - оптимальный баланс между:
- Простотой реализации
- Улучшением пользовательского опыта
- Единообразием с командой `/trash`
- Минимальными изменениями кода
