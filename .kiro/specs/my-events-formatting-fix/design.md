# Проектирование: Исправление форматирования списка "Мои события" после редактирования

## Обзор

Проблема возникает из-за того, что при редактировании события система обновляет только одно сообщение с событием, не учитывая, что это может быть первое событие в списке, которое должно содержать шапку. Кроме того, метод `buildEventMessage` в `BotMessageBuilder` использует другой формат отображения по сравнению с `formatEvent` в `MyEventsCommandHandler`.

### Текущая архитектура

1. **MyEventsCommandHandler** - отображает список событий:
   - Формирует шапку через `buildHeader()`
   - Форматирует первое событие через `formatEvent()`
   - Объединяет шапку с первым событием в одно сообщение
   - Остальные события отправляет отдельными сообщениями

2. **BotMessageBuilder.buildEventMessage()** - форматирует отдельное событие:
   - Используется при обновлении событий после редактирования
   - НЕ включает шапку списка
   - Использует другой формат (эмодзи статуса, другие отступы)

3. **EventService.sendOrUpdateEventMessage()** - обновляет сообщение о событии:
   - Использует `buildEventMessage()` для форматирования
   - Обновляет существующее сообщение через `editMessageText`
   - Не знает, является ли это первым событием в списке

### Корневая причина проблем

1. **Потеря шапки**: При редактировании первого события система обновляет только текст события, теряя шапку "📋 Мои события"
2. **Несогласованность форматирования**: `formatEvent()` и `buildEventMessage()` используют разные форматы
3. **Отсутствие контекста**: Система не знает, что сообщение является частью списка "Мои события"

## Архитектура решения

### Подход 1: Унификация форматирования (Рекомендуемый)

Использовать единый метод форматирования для всех случаев отображения событий.

**Преимущества:**
- Единообразное отображение событий
- Проще поддерживать
- Меньше дублирования кода

**Недостатки:**
- Требует рефакторинга существующего кода

### Подход 2: Контекстное форматирование

Передавать контекст (является ли событие первым в списке) при форматировании.

**Преимущества:**
- Минимальные изменения в существующем коде

**Недостатки:**
- Усложняет логику
- Требует передачи дополнительных параметров

**Выбранный подход:** Подход 1 - Унификация форматирования

## Компоненты и интерфейсы

### 1. MarkdownFormatter (без изменений)

Утилитный класс для экранирования и форматирования MarkdownV2.

### 2. BotMessageBuilder (изменения)

```java
/**
 * Форматирует событие для отображения в списке "Мои события".
 * Использует единый формат для всех случаев отображения.
 */
public String buildEventMessage(Event event) {
    // Формат:
    // 📌 *Название события*
    // 📅 Дата: DD.MM.YYYY
    // 🕐 Время: HH:MM
    // 📝 Описание: текст (если есть)
}

/**
 * Форматирует список событий с шапкой для команды /my_events.
 * Первое событие объединяется с шапкой в одно сообщение.
 */
public String buildMyEventsHeader(int eventCount) {
    // Формат:
    // 📋 *Мои события*
    // 
    // Всего событий: N
}
```

### 3. MyEventsCommandHandler (изменения)

```java
/**
 * Использует BotMessageBuilder.buildEventMessage() вместо formatEvent()
 * для единообразного форматирования.
 */
private String formatEvent(Event event) {
    return botMessageBuilder.buildEventMessage(event);
}

/**
 * Использует BotMessageBuilder.buildMyEventsHeader() вместо buildHeader()
 */
private String buildHeader(int eventCount) {
    return botMessageBuilder.buildMyEventsHeader(eventCount);
}
```

### 4. EventService (без изменений)

Продолжает использовать `BotMessageBuilder.buildEventMessage()`, который теперь будет давать единообразный формат.

## Свойства корректности

*Свойство - это характеристика или поведение, которое должно выполняться во всех допустимых выполнениях системы - по сути, формальное утверждение о том, что система должна делать. Свойства служат мостом между человекочитаемыми спецификациями и машинопроверяемыми гарантиями корректности.*

### Свойство 1: Единообразие форматирования событий

*Для любого* события, независимо от контекста отображения (первоначальный список, обновление после редактирования, отдельное сообщение), форматирование должно быть идентичным.

**Проверяет: Требования 1.1, 1.5**

### Свойство 2: Сохранение шапки при обновлении первого события

*Для любого* списка событий, если первое событие редактируется, шапка "📋 Мои события\nВсего событий: N" должна сохраняться в обновленном сообщении.

**Проверяет: Требования 2.1, 2.2**

### Свойство 3: Корректное размещение эмодзи

*Для любого* события, эмодзи должны размещаться с правильными отступами: один пробел после эмодзи перед текстом, эмодзи полей на новых строках.

**Проверяет: Требования 3.1, 3.2, 3.3, 3.4, 3.5**

### Свойство 4: Централизация форматирования

*Для любого* места в коде, где требуется форматирование события, должен использоваться единый метод из BotMessageBuilder.

**Проверяет: Требования 4.1, 4.2, 4.3**

## Обработка ошибок

### 1. Ошибки форматирования MarkdownV2

**Стратегия:** Использовать существующий fallback механизм в `TelegramMessageService`
- При ошибке 400 (Bad Request) отправлять сообщение без форматирования
- Логировать ошибки для анализа

### 2. Отсутствие messageId

**Стратегия:** Отправлять новое сообщение вместо обновления существующего
- Проверять наличие messageId перед попыткой обновления
- Сохранять новый messageId в базе данных

### 3. Удаленное пользователем сообщение

**Стратегия:** Обрабатывать через `tryEditMessageText`
- Метод возвращает false, если сообщение не найдено
- Отправлять новое сообщение при неудаче обновления

## Стратегия тестирования

### Unit-тесты

1. **BotMessageBuilder.buildEventMessage()**
   - Проверка корректного форматирования всех полей события
   - Проверка экранирования специальных символов
   - Проверка обработки null значений
   - Проверка размещения эмодзи с правильными отступами

2. **BotMessageBuilder.buildMyEventsHeader()**
   - Проверка корректного форматирования шапки
   - Проверка правильного отображения количества событий

3. **MyEventsCommandHandler.handle()**
   - Проверка объединения шапки с первым событием
   - Проверка отправки остальных событий отдельно
   - Проверка использования единого метода форматирования

### Property-Based тесты

1. **Свойство 1: Единообразие форматирования**
   - Генерировать случайные события
   - Форматировать через `buildEventMessage()`
   - Проверять, что формат соответствует ожидаемому шаблону

2. **Свойство 3: Корректное размещение эмодзи**
   - Генерировать события с различными комбинациями полей
   - Проверять, что эмодзи всегда имеют один пробел после себя
   - Проверять, что эмодзи полей на новых строках

### Integration тесты

1. **Редактирование первого события**
   - Создать список из нескольких событий
   - Отредактировать первое событие
   - Проверить, что шапка сохранилась
   - Проверить, что форматирование корректное

2. **Редактирование не первого события**
   - Создать список из нескольких событий
   - Отредактировать второе или последующее событие
   - Проверить, что форматирование корректное

## Детали реализации

### Шаг 1: Рефакторинг BotMessageBuilder

1. Переименовать текущий `buildEventMessage()` в `buildEventMessageWithStatus()` (если нужно сохранить старую логику)
2. Создать новый `buildEventMessage()` с форматом из `MyEventsCommandHandler.formatEvent()`
3. Создать `buildMyEventsHeader()` с логикой из `MyEventsCommandHandler.buildHeader()`

### Шаг 2: Обновление MyEventsCommandHandler

1. Удалить методы `formatEvent()` и `buildHeader()`
2. Использовать `botMessageBuilder.buildEventMessage()` и `botMessageBuilder.buildMyEventsHeader()`
3. Убедиться, что логика объединения шапки с первым событием сохранена

### Шаг 3: Проверка других использований

1. Проверить все места, где используется `buildEventMessage()`
2. Убедиться, что новый формат подходит для всех случаев
3. При необходимости создать отдельные методы для специфичных форматов

### Шаг 4: Тестирование

1. Запустить существующие тесты
2. Добавить новые unit-тесты для измененных методов
3. Добавить integration тесты для проверки сценариев редактирования

## Альтернативные решения

### Альтернатива 1: Хранение контекста списка

Хранить в базе данных информацию о том, что событие является первым в списке "Мои события".

**Отклонено:** Усложняет модель данных и логику без существенных преимуществ.

### Альтернатива 2: Всегда отправлять шапку отдельно

Отправлять шапку "Мои события" отдельным сообщением, а не объединять с первым событием.

**Отклонено:** Нарушает текущий UX и требует изменения логики отображения.

### Альтернатива 3: Не обновлять сообщения, а пересылать список заново

При редактировании любого события удалять все сообщения списка и отправлять заново.

**Отклонено:** Плохой UX, пользователь теряет контекст, лишний трафик.

## Метрики успеха

1. **Единообразие форматирования**: Все события отображаются в едином формате
2. **Сохранение шапки**: При редактировании первого события шапка не теряется
3. **Корректные отступы**: Эмодзи размещаются с правильными пробелами
4. **Отсутствие регрессий**: Все существующие тесты проходят
5. **Покрытие тестами**: Новый код покрыт unit и integration тестами
