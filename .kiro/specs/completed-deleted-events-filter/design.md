# Проектирование: Фильтрация завершенных и удаленных событий

## Обзор

Данный документ описывает проектное решение для исправления проблемы отображения завершенных (COMPLETED) и удаленных (DELETED) событий в списках команд `/upcoming_events`, `/today` и `/week`. Текущая реализация использует метод `EventRepository.findByFamilyIdAndEventDateBetween()`, который не фильтрует события по статусу, что приводит к отображению неактуальных событий.

## Архитектура

### Текущая архитектура

```
CommandHandler (UpcomingEventsCommandHandler, TodayCommandHandler, WeekCommandHandler)
    ↓
EventService.getUpcomingEvents(familyId, days)
    ↓
EventRepository.findByFamilyIdAndEventDateBetween(familyId, startDate, endDate)
    ↓
Возвращает ВСЕ события (включая COMPLETED и DELETED)
```

### Целевая архитектура

```
CommandHandler (UpcomingEventsCommandHandler, TodayCommandHandler, WeekCommandHandler)
    ↓
EventService.getUpcomingEvents(familyId, days)
    ↓
EventRepository.findByFamilyIdAndEventDateBetweenAndStatus(familyId, startDate, endDate, ACTIVE)
    ↓
Возвращает ТОЛЬКО активные события (ACTIVE)
```

## Компоненты и интерфейсы

### EventService

**Изменяемый метод:**
```java
@Transactional(readOnly = true)
public List<Event> getUpcomingEvents(Long familyId, int days)
```

**Изменения:**
- Заменить вызов `findByFamilyIdAndEventDateBetween()` на `findByFamilyIdAndEventDateBetweenAndStatus()`
- Передать `Event.EventStatus.ACTIVE` в качестве параметра статуса
- Обновить логирование для отражения фильтрации по статусу

### EventRepository

**Используемый метод (уже существует):**
```java
@EntityGraph(attributePaths = {"user", "family"})
List<Event> findByFamilyIdAndEventDateBetweenAndStatus(
    Long familyId, 
    LocalDate startDate, 
    LocalDate endDate,
    Event.EventStatus status
);
```

Этот метод уже реализован в репозитории и готов к использованию.

### CommandHandlers

Обработчики команд не требуют изменений, так как они используют `EventService.getUpcomingEvents()`, который будет исправлен.

## Модели данных

### Event.EventStatus

Существующий enum со следующими значениями:
- `DRAFT` - черновик события (в процессе создания)
- `ACTIVE` - активное событие (должно отображаться в списках)
- `COMPLETED` - завершенное событие (не должно отображаться)
- `DELETED` - удаленное событие (не должно отображаться, доступно в корзине)

## Свойства корректности

*Свойство - это характеристика или поведение, которое должно выполняться для всех допустимых выполнений системы - по сути, формальное утверждение о том, что должна делать система. Свойства служат мостом между человекочитаемыми спецификациями и машинно-проверяемыми гарантиями корректности.*

### Свойство 1: Фильтрация по статусу ACTIVE

*Для любого* запроса предстоящих событий семьи, все возвращенные события должны иметь статус ACTIVE

**Проверяет: Требования 1.1, 2.1, 3.1**

### Свойство 2: Исключение завершенных событий

*Для любого* запроса предстоящих событий семьи, ни одно событие со статусом COMPLETED не должно присутствовать в результатах

**Проверяет: Требования 1.2, 2.2, 3.2**

### Свойство 3: Исключение удаленных событий

*Для любого* запроса предстоящих событий семьи, ни одно событие со статусом DELETED не должно присутствовать в результатах

**Проверяет: Требования 1.3, 2.3, 3.3**

### Свойство 4: Исключение черновиков

*Для любого* запроса предстоящих событий семьи, ни одно событие со статусом DRAFT не должно присутствовать в результатах

**Проверяет: Требования 1.4, 2.4, 3.4**

### Свойство 5: Консистентность фильтрации

*Для любых* двух последовательных вызовов метода getUpcomingEvents с одинаковыми параметрами (при отсутствии изменений в БД), результаты должны содержать одинаковый набор событий

**Проверяет: Требования 4.2**

## Обработка ошибок

### Существующая обработка

Метод `getUpcomingEvents()` уже содержит валидацию:
- Проверка `days <= 0` с выбросом `IllegalArgumentException`

### Дополнительная обработка

Не требуется, так как:
- Метод репозитория безопасен для null-значений (Spring Data JPA)
- Enum `EventStatus.ACTIVE` всегда валиден
- Логирование уже присутствует в методе

## Влияние на производительность

### Текущая производительность

Метод `findByFamilyIdAndEventDateBetween()` использует индекс `idx_events_family_date`:
```sql
@Index(name = "idx_events_family_date", columnList = "family_id, event_date")
```

### Целевая производительность

Метод `findByFamilyIdAndEventDateBetweenAndStatus()` использует тот же индекс плюс индекс по статусу:
```sql
@Index(name = "idx_events_status", columnList = "status")
```

**Ожидаемое улучшение:**
- Меньше данных возвращается из БД (фильтрация на уровне SQL)
- Меньше нагрузка на сеть между приложением и БД
- Меньше памяти используется для хранения результатов
- Быстрее обработка в Java (меньше объектов для фильтрации)

## Обратная совместимость

### Изменения в API

Публичный API `EventService.getUpcomingEvents()` не изменяется:
- Сигнатура метода остается прежней
- Возвращаемый тип не меняется
- Параметры не меняются

### Изменения в поведении

**Изменение:** Метод теперь возвращает только активные события вместо всех событий.

**Влияние:** Это исправление бага, а не breaking change. Текущее поведение (возврат завершенных и удаленных событий) является ошибочным и не соответствует ожиданиям пользователей.

## Миграция данных

Миграция данных не требуется. Изменения касаются только логики запросов, структура БД остается неизменной.

## Мониторинг и логирование

### Существующее логирование

```java
log.debug("Получение предстоящих событий для семьи ID={} на {} дней", familyId, days);
log.debug("Найдено {} предстоящих событий для семьи ID={}", events.size(), familyId);
```

### Обновленное логирование

```java
log.debug("Получение активных предстоящих событий для семьи ID={} на {} дней", familyId, days);
log.debug("Найдено {} активных предстоящих событий для семьи ID={}", events.size(), familyId);
```

Добавление слова "активных" поможет при отладке понять, что применяется фильтрация по статусу.

## Альтернативные решения

### Альтернатива 1: Фильтрация в Java коде

**Описание:** Оставить текущий метод репозитория, но добавить фильтрацию в `EventService`:
```java
return events.stream()
    .filter(event -> event.getStatus() == Event.EventStatus.ACTIVE)
    .collect(Collectors.toList());
```

**Недостатки:**
- Неэффективно: загружаются лишние данные из БД
- Больше нагрузка на сеть и память
- Дублирование логики фильтрации в разных местах

**Вывод:** Отклонено в пользу фильтрации на уровне БД

### Альтернатива 2: Создание нового метода в EventService

**Описание:** Создать новый метод `getActiveUpcomingEvents()`, оставив старый без изменений.

**Недостатки:**
- Увеличение API surface
- Риск использования неправильного метода
- Старый метод останется источником багов

**Вывод:** Отклонено, так как старый метод содержит баг и должен быть исправлен

### Альтернатива 3: Изменение метода репозитория по умолчанию

**Описание:** Изменить `findByFamilyIdAndEventDateBetween()` чтобы он фильтровал по статусу.

**Недостатки:**
- Может сломать другие части системы, использующие этот метод
- Нарушает принцип наименьшего удивления (метод без упоминания статуса не должен фильтровать)

**Вывод:** Отклонено, используем существующий метод с явным указанием статуса

## Выбранное решение

Использовать существующий метод `findByFamilyIdAndEventDateBetweenAndStatus()` с параметром `Event.EventStatus.ACTIVE` в методе `EventService.getUpcomingEvents()`.

**Преимущества:**
- Минимальные изменения кода (одна строка)
- Использование существующей инфраструктуры
- Оптимальная производительность (фильтрация на уровне БД)
- Явная семантика (метод четко указывает на фильтрацию по статусу)
- Консистентность с другими методами сервиса (например, `getUserEvents()` уже использует фильтрацию по статусу)
