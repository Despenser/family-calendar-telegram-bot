# Проектирование: Сохранение шапки "Мои события" при редактировании первого события

## Обзор

Проблема заключается в том, что при редактировании первого события в списке "Мои события" система обновляет сообщение через `EventService.sendOrUpdateEventMessage()`, который форматирует только само событие без шапки. Это приводит к потере заголовка "📋 Мои события" и информации о количестве событий.

### Текущая архитектура

1. **MyEventsCommandHandler.handle()** - отображает список событий:
   - Формирует шапку через `botMessageBuilder.buildMyEventsHeader()`
   - Форматирует первое событие через `botMessageBuilder.buildEventMessage()`
   - Объединяет шапку с первым событием: `header + "\n" + firstEventText`
   - Отправляет объединенное сообщение и сохраняет messageId в базе
   - Остальные события отправляет отдельно

2. **EventService.sendOrUpdateEventMessage()** - обновляет сообщение о событии:
   - Форматирует событие через `botMessageBuilder.buildEventMessage()`
   - Если есть messageId, обновляет существующее сообщение
   - НЕ знает, что сообщение может содержать шапку списка

3. **Event.messageId** - хранит идентификатор сообщения в Telegram:
   - Используется для обновления сообщения
   - НЕ содержит информации о том, является ли сообщение первым в списке

### Корневая причина проблемы

Система не хранит информацию о том, что данное сообщение является первым в списке "Мои события" и должно содержать шапку при обновлении.

**Дополнительная проблема:** Обработчики callback (DateTimeCallbackHandler, TextEventCallbackHandler и др.) при редактировании события вызывают `messageService.editMessageText()` напрямую, используя только `botMessageBuilder.buildEventMessage(event)`, который НЕ проверяет флаг `isMyEventsHeader` и не добавляет шапку. Это приводит к потере шапки даже после реализации основного решения.

## Архитектура решения

### Выбранный подход: Добавление флага в модель Event

Добавим в модель `Event` поле `isMyEventsHeader`, которое будет указывать, что сообщение этого события содержит шапку списка "Мои события".

**Преимущества:**
- Минимальные изменения в существующей архитектуре
- Информация хранится в базе данных и доступна в любом месте
- Не требует передачи дополнительных параметров через слои
- Легко поддерживать актуальность при изменении списка событий

**Недостатки:**
- Требует миграции базы данных
- Нужно обновлять флаг при изменении порядка событий

### 2. EventService (изменения)

```java
/**
 * Отправляет или обновляет сообщение о событии.
 * Если событие помечено как первое в списке "Мои события" (isMyEventsHeader = true),
 * добавляет шапку списка перед текстом события.
 */
public Event sendOrUpdateEventMessage(Event event, Long chatId) throws TelegramApiException {
    // Форматирование текста сообщения
    String messageText = botMessageBuilder.buildEventMessage(event);
    
    // Если это первое событие в списке "Мои события", добавляем шапку
    if (Boolean.TRUE.equals(event.getIsMyEventsHeader())) {
        int eventCount = getActiveEventsCount(event.getUser().getId());
        String header = botMessageBuilder.buildMyEventsHeader(eventCount);
        messageText = header + "\n" + messageText;
    }
    
    // ... остальная логика отправки/обновления ...
}

/**
 * Получает количество активных событий пользователя.
 */
private int getActiveEventsCount(Long userId) {
    return eventRepository.countByUserIdAndStatusNot(userId, Event.EventStatus.DELETED);
}
```

### 3. MyEventsCommandHandler (изменения)

```java
@Override
public String handle(Message message, User user) {
    // ... получение событий ...

    Event firstEvent = userEvents.get(0);

    if (!Boolean.TRUE.equals(firstEvent.getIsMyEventsHeader())) {
        firstEvent.setIsMyEventsHeader(true);
        eventService.saveEvent(firstEvent);

    for (int i = 1; i < userEvents.size(); i++) {
        Event event = userEvents.get(i);
        if (Boolean.TRUE.equals(event.getIsMyEventsHeader())) {
            event.setIsMyEventsHeader(false);
            eventService.saveEvent(event);
        }
    }
    
    // Формируем и отправляем сообщения как раньше
    // ...
}
```

### 4. EventService.deleteEvent() (изменения)

```java
/**
 * Удаляет событие и обновляет флаг шапки для следующего события, если удаляется первое.
 */
@Transactional
public void deleteEvent(Long eventId, Long userId) {
    Event event = getEventById(eventId);
    
    // Проверка прав доступа
    // ...
    
    // Если удаляется первое событие в списке "Мои события"
    if (Boolean.TRUE.equals(event.getIsMyEventsHeader())) {
        // Находим следующее событие пользователя по дате
        List<Event> userEvents = getUserEvents(userId);
        if (userEvents.size() > 1) {
            // Находим следующее событие (не удаляемое)
            Event nextEvent = userEvents.stream()
                .filter(e -> !e.getId().equals(eventId))
                .findFirst()
                .orElse(null);
            
            if (nextEvent != null) {
                nextEvent.setIsMyEventsHeader(true);
                saveEvent(nextEvent);
                
                // Обновляем сообщение следующего события с шапкой
                try {
                    sendOrUpdateEventMessage(nextEvent, event.getUser().getTelegramId());
                } catch (TelegramApiException e) {
                    log.error("Не удалось обновить сообщение нового первого события: {}", e.getMessage());
                }
            }
        }
    }
    
    // Удаление события
    event.setStatus(Event.EventStatus.DELETED);
    saveEvent(event);
}
```

### 5. Обработчики Callback (новые изменения)

**Проблема:** Обработчики callback (DateTimeCallbackHandler, TextEventCallbackHandler и др.) при редактировании события вызывают `messageService.editMessageText()` напрямую, что приводит к потере шапки.

**Решение:** Создать вспомогательный метод для формирования текста сообщения с учетом флага шапки.

#### 5.1. BotMessageBuilder (новый метод)

```java
/**
 * Формирует текст сообщения о событии с учетом флага isMyEventsHeader.
 * Если событие помечено как первое в списке "Мои события", добавляет шапку.
 * 
 * @param event событие для форматирования
 * @param eventCount количество активных событий пользователя (используется только если isMyEventsHeader = true)
 * @return отформатированный текст сообщения
 */
public String buildEventMessageWithHeader(Event event, int eventCount) {
    String messageText = buildEventMessage(event);
    
    // Если это первое событие в списке "Мои события", добавляем шапку
    if (Boolean.TRUE.equals(event.getIsMyEventsHeader())) {
        String header = buildMyEventsHeader(eventCount);
        messageText = header + "\n" + messageText;
    }
    
    return messageText;
}
```

## Модели данных

### Миграция базы данных

```sql
-- V14__Add_is_my_events_header_to_events.sql

ALTER TABLE events 
ADD COLUMN is_my_events_header BOOLEAN DEFAULT FALSE;

-- Устанавливаем флаг для первых событий каждого пользователя
WITH first_events AS (
    SELECT DISTINCT ON (user_id) id
    FROM events
    WHERE status != 'DELETED'
    ORDER BY user_id, event_date, event_time, id
)
UPDATE events
SET is_my_events_header = TRUE
WHERE id IN (SELECT id FROM first_events);
```

## Свойства корректности

*Свойство - это характеристика или поведение, которое должно выполняться во всех допустимых выполнениях системы - по сути, формальное утверждение о том, что система должна делать. Свойства служат мостом между человекочитаемыми спецификациями и машинопроверяемыми гарантиями корректности.*

### Свойство 1: Сохранение шапки при обновлении первого события

*Для любого* события с флагом `isMyEventsHeader = true`, при форматировании сообщения через `sendOrUpdateEventMessage()` результирующий текст должен начинаться с шапки "📋 *Мои события*" и содержать строку "Всего событий: N", где N - количество активных событий пользователя.

**Проверяет: Требования 1.1, 1.2**

### Свойство 2: Отсутствие шапки для не первых событий

*Для любого* события с флагом `isMyEventsHeader = false` или `null`, при форматировании сообщения через `sendOrUpdateEventMessage()` результирующий текст НЕ должен содержать строку "📋 *Мои события*".

**Проверяет: Требования 1.3**

### Свойство 3: Передача флага при удалении первого события

*Для любого* списка событий пользователя с размером >= 2, при удалении события с флагом `isMyEventsHeader = true`, следующее событие по дате (самое раннее из оставшихся) должно получить флаг `isMyEventsHeader = true`, а у удаленного события флаг должен быть сброшен.

**Проверяет: Требования 2.3, 4.1, 4.2**

### Свойство 4: Установка флага для нового первого события

*Для любого* пользователя, при вызове команды /my_events, событие с самой ранней датой и временем должно иметь флаг `isMyEventsHeader = true`, а все остальные активные события должны иметь флаг `isMyEventsHeader = false`.

**Проверяет: Требования 2.1, 2.4**

### Свойство 5: Корректность количества событий в шапке

*Для любого* события с флагом `isMyEventsHeader = true`, при форматировании сообщения число N в строке "Всего событий: N" должно быть равно количеству активных (не удаленных) событий пользователя.

**Проверяет: Требования 1.4**

### Свойство 6: Сохранение шапки при редактировании через callback handlers

*Для любого* события с флагом `isMyEventsHeader = true`, при редактировании через обработчики callback (изменение даты, времени, названия и т.д.) результирующее обновленное сообщение должно содержать шапку "📋 *Мои события*" и корректное количество событий.

**Проверяет: Требования 1.1, 1.2, 3.5**

## Обработка ошибок

### 1. Ошибка обновления сообщения нового первого события

**Стратегия:** Логировать ошибку, но не прерывать удаление
- Событие все равно удаляется
- Флаг передается следующему событию
- Пользователь может вызвать /my_events для обновления списка

### 2. Отсутствие следующего события при удалении первого

**Стратегия:** Просто удалить событие без передачи флага
- Если это последнее событие, флаг не нужен
- При следующем вызове /my_events флаг будет установлен корректно

### 3. Несколько событий с флагом isMyEventsHeader

**Стратегия:** При вызове /my_events сбросить все флаги и установить только для первого
- Это исправит любые несоответствия в данных
- Гарантирует корректность после каждого вызова команды

## Альтернативные решения

### Альтернатива 1: Передача контекста через параметры

Передавать информацию о необходимости шапки через параметры методов.

**Отклонено:** 
- Требует изменения сигнатур многих методов
- Усложняет код
- Нарушает принцип единственной ответственности

### Альтернатива 2: Хранение контекста в ConversationStateService

Хранить информацию о том, что сообщение является первым в списке, в состоянии разговора.

**Отклонено:**
- ConversationStateService предназначен для временного состояния диалога
- Информация может потеряться при перезапуске приложения
- Сложнее поддерживать актуальность

### Альтернатива 3: Всегда пересылать весь список при изменении

При редактировании любого события удалять все сообщения и отправлять список заново.

**Отклонено:**
- Плохой UX - пользователь теряет контекст
- Лишний трафик и нагрузка на Telegram API
- Может раздражать пользователей

### Альтернатива 4: Отправлять шапку отдельным сообщением

Отправлять шапку "Мои события" отдельным сообщением, не объединяя с первым событием.

**Отклонено:**
- Нарушает текущий UX
- Требует изменения логики отображения
- Увеличивает количество сообщений в чате

## Метрики успеха

1. **Сохранение шапки**: При редактировании первого события шапка не теряется
2. **Корректность количества**: Число событий в шапке всегда актуально
3. **Передача флага**: При удалении первого события флаг корректно передается следующему
4. **Отсутствие регрессий**: Все существующие тесты проходят
5. **Покрытие тестами**: Новый код покрыт unit и integration тестами
6. **Производительность**: Нет заметного снижения производительности при работе со списком событий
