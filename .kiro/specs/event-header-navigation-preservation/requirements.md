# Requirements Document

## Introduction

Данный документ описывает требования к исправлению бага с потерей шапки события при навигации между событием и его вложениями в Telegram боте семейного календаря. 

Проблема заключается в следующем: когда пользователь открывает список "Мои события", первое событие отображается с шапкой "📋 **Мои события**\n\nВсего событий: N". При переходе из этого события в раздел "Вложения" и последующем возврате обратно к событию, шапка теряется и отображается только само событие без заголовка.

Шапка события - это важный элемент интерфейса, который:
- Показывает пользователю контекст просмотра (что он находится в списке "Мои события")
- Отображает общее количество событий пользователя
- Обеспечивает визуальную группировку и структурирование информации

Потеря шапки при навигации создает неконсистентный пользовательский опыт и нарушает логику отображения списка событий.

## Glossary

- **Event_Header** (Шапка события): Заголовочная часть сообщения, отображаемая над первым событием в списке "Мои события". Содержит эмодзи 📋, текст "Мои события" и счетчик "Всего событий: N". Пример: "📋 **Мои события**\n\nВсего событий: 3\n"
- **Attachment_View** (Просмотр вложений): Экран со списком вложений к событию
- **Navigation_Context** (Контекст навигации): Сохраненная информация о наличии шапки события и количестве событий для корректного восстановления при возврате
- **Event_Card** (Карточка события): Сообщение с полной информацией о событии и кнопками управления
- **Attachment_Handler** (Обработчик вложений): Компонент AttachmentCallbackHandler, отвечающий за обработку действий с вложениями
- **My_Events_List** (Список "Мои события"): Список активных событий пользователя, где первое событие отображается с шапкой

## Requirements

### Requirement 1: Сохранение контекста шапки при переходе к вложениям

**User Story:** Как пользователь, я хочу, чтобы при переходе из события во вложения сохранялась информация о шапке события, чтобы при возврате шапка отображалась корректно.

#### Acceptance Criteria

1. WHEN пользователь открывает список вложений из карточки события, THEN THE System SHALL сохранить текущий контекст шапки события перед переходом
2. WHEN контекст шапки сохраняется, THEN THE System SHALL сохранить флаг наличия шапки и количество событий
3. WHEN пользователь находится в просмотре вложений, THEN THE System SHALL хранить контекст шапки в памяти до возврата к событию

### Requirement 2: Восстановление шапки при возврате к событию

**User Story:** Как пользователь, я хочу, чтобы при возврате из вложений к событию шапка восстанавливалась в исходном виде, чтобы не терять контекст просмотра.

#### Acceptance Criteria

1. WHEN пользователь возвращается из списка вложений к карточке события, THEN THE System SHALL восстановить шапку события из сохраненного контекста
2. WHEN шапка восстанавливается, THEN THE System SHALL использовать сохраненное количество событий для формирования текста шапки
3. WHEN контекст шапки отсутствует, THEN THE System SHALL отобразить событие без шапки
4. WHEN шапка успешно восстановлена, THEN THE System SHALL очистить временный контекст вложений

### Requirement 3: Корректная обработка отсутствия контекста

**User Story:** Как разработчик, я хочу, чтобы система корректно обрабатывала случаи отсутствия контекста шапки, чтобы избежать ошибок при навигации.

#### Acceptance Criteria

1. WHEN контекст шапки не найден при возврате к событию, THEN THE System SHALL отобразить событие без шапки
2. WHEN происходит ошибка при получении контекста, THEN THE System SHALL залогировать ошибку и продолжить работу без шапки
3. WHEN пользователь открывает событие напрямую (не из списка "Мои события"), THEN THE System SHALL отобразить событие без шапки

### Requirement 4: Логирование операций с контекстом

**User Story:** Как разработчик, я хочу видеть подробные логи операций с контекстом шапки, чтобы отслеживать и диагностировать проблемы.

#### Acceptance Criteria

1. WHEN контекст шапки сохраняется, THEN THE System SHALL залогировать операцию на уровне DEBUG с указанием userId, eventId и параметров контекста
2. WHEN контекст шапки восстанавливается, THEN THE System SHALL залогировать операцию на уровне DEBUG с указанием найденных параметров
3. WHEN контекст шапки не найден, THEN THE System SHALL залогировать это на уровне DEBUG
4. WHEN происходит ошибка при работе с контекстом, THEN THE System SHALL залогировать ошибку на уровне ERROR с полным stack trace

### Requirement 5: Интеграция с существующим механизмом сохранения контекста

**User Story:** Как разработчик, я хочу использовать существующий механизм ConversationStateService для сохранения контекста шапки, чтобы не дублировать логику.

#### Acceptance Criteria

1. WHEN требуется сохранить контекст шапки, THEN THE System SHALL использовать метод saveEventHeaderContext из ConversationStateService
2. WHEN требуется получить контекст шапки, THEN THE System SHALL использовать метод getEventHeaderContext из ConversationStateService
3. WHEN требуется очистить контекст шапки, THEN THE System SHALL использовать метод clearEventHeaderContext из ConversationStateService
4. THE System SHALL использовать класс EventHeaderContext для передачи данных контекста

### Requirement 6: Сохранение контекста при открытии вложений

**User Story:** Как пользователь, я хочу, чтобы при нажатии кнопки "Вложения" система сохраняла текущий контекст, чтобы при возврате все отображалось корректно.

#### Acceptance Criteria

1. WHEN пользователь нажимает кнопку "Вложения" в карточке события, THEN THE System SHALL проверить наличие текущего контекста шапки
2. IF контекст шапки существует, THEN THE System SHALL сохранить его перед переходом к списку вложений
3. WHEN переход к вложениям завершен, THEN THE System SHALL сохранить messageId для последующего редактирования

### Requirement 7: Тестирование механизма сохранения и восстановления

**User Story:** Как разработчик, я хочу иметь автоматические тесты для механизма сохранения и восстановления контекста, чтобы гарантировать корректность работы.

#### Acceptance Criteria

1. THE System SHALL иметь unit-тесты для проверки сохранения контекста при переходе к вложениям
2. THE System SHALL иметь unit-тесты для проверки восстановления контекста при возврате к событию
3. THE System SHALL иметь unit-тесты для проверки обработки отсутствия контекста
4. THE System SHALL иметь integration-тесты для проверки полного цикла навигации: событие → вложения → событие
