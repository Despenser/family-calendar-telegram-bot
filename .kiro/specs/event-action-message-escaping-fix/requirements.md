# Requirements Document: Исправление экранирования в сообщениях о действиях с событиями

## Introduction

При отправке сообщений пользователям возникают ошибки парсинга MarkdownV2 из-за неправильного использования методов форматирования. Telegram API возвращает ошибку 400 "can't parse entities".

Найдено два типа проблем:

**Тип 1: Ручное экранирование внутри formatMessage()**
- MyEventsCommandHandler - сообщения об ошибках (строки 407, 436, 456, 460)
- UpdateProcessor - сообщения об ошибках и отмене редактирования (строки 988, 1890, 1963, 2093)
- Проблема: используется `\\.` внутри вызовов formatMessage(), что приводит к двойному экранированию

**Тип 2: Ручная конкатенация escape() + bold() вместо formatMessage()**
- MyEventsCommandHandler - сообщение об отсутствии событий (строка 218)
- WeekCommandHandler - сообщение об отсутствии событий (строка 96)
- StartCommandHandler - сообщение для незарегистрированных (строка 220)
- TodayCommandHandler - сообщение об отсутствии событий (строка 99)
- TrashCommandHandler - сообщения о корзине, восстановлении, удалении (строки 72, 193, 225)
- UpcomingEventsCommandHandler - сообщение об отсутствии событий (строка 189)
- Проблема: используется ручная конкатенация `escape() + bold() + escape()` вместо `formatMessage()`

**Тип 3: Жирный текст внутри строк formatMessage()**
- UpdateProcessor - сообщения о создании события (строки 694, 763, 1575)
- StatsCommandHandler - статистика (строки 82-94)
- Проблема: используется `*текст*` внутри строки formatMessage вместо вызова bold()

## Glossary

- **MarkdownV2**: Формат разметки текста Telegram, требующий экранирования специальных символов
- **MarkdownFormatter**: Утилитный класс для форматирования и экранирования текста в MarkdownV2
- **formatMessage**: Метод MarkdownFormatter для форматирования сообщений с автоматическим экранированием
- **bold**: Метод MarkdownFormatter для форматирования текста жирным шрифтом с экранированием
- **code**: Метод MarkdownFormatter для форматирования текста моноширинным шрифтом
- **escape**: Метод MarkdownFormatter для экранирования специальных символов MarkdownV2

## Requirements

### Requirement 1: Исправление сообщений об ошибках в MyEventsCommandHandler

**User Story:** Как пользователь, я хочу получать корректные сообщения об ошибках при работе с событиями, чтобы видеть информацию без ошибок парсинга.

#### Acceptance Criteria

1. WHEN происходит ошибка загрузки деталей события (строка 407) THEN система SHALL отправить корректно отформатированное сообщение без ручного экранирования
2. WHEN пользователь не имеет прав для редактирования (строка 436) THEN система SHALL отправить корректно отформатированное сообщение без ручного экранирования
3. WHEN событие не найдено при удалении (строка 456) THEN система SHALL отправить корректно отформатированное сообщение без ручного экранирования
4. WHEN происходит ошибка при начале редактирования (строка 460) THEN система SHALL отправить корректно отформатированное сообщение без ручного экранирования
5. WHEN сообщения об ошибках отправляются THEN Telegram API SHALL успешно распарсить MarkdownV2 без ошибок 400

### Requirement 2: Исправление сообщений об ошибках в UpdateProcessor

**User Story:** Как пользователь, я хочу получать корректные сообщения при работе с редактированием событий, чтобы видеть информацию без ошибок парсинга.

#### Acceptance Criteria

1. WHEN происходит общая ошибка (строка 988) THEN система SHALL отправить корректно отформатированное сообщение без ручного экранирования
2. WHEN событие не найдено при редактировании (строки 1890, 1963) THEN система SHALL отправить корректно отформатированное сообщение без ручного экранирования
3. WHEN пользователь отменяет редактирование (строка 2093) THEN система SHALL отправить корректно отформатированное сообщение без ручного экранирования
4. WHEN сообщения об ошибках и отмене отправляются THEN Telegram API SHALL успешно распарсить MarkdownV2 без ошибок 400

### Requirement 3: Исправление ручной конкатенации в обработчиках команд

**User Story:** Как пользователь, я хочу получать корректные сообщения от всех команд бота, чтобы видеть информацию без ошибок парсинга.

#### Acceptance Criteria

1. WHEN используется форматирование сообщений THEN система SHALL использовать formatMessage() вместо ручной конкатенации escape() + bold()
2. WHEN формируется сообщение об отсутствии событий в MyEventsCommandHandler (строка 218) THEN система SHALL использовать formatMessage()
3. WHEN формируется сообщение об отсутствии событий в WeekCommandHandler (строка 96) THEN система SHALL использовать formatMessage()
4. WHEN формируется сообщение для незарегистрированных в StartCommandHandler (строка 220) THEN система SHALL использовать formatMessage()
5. WHEN формируется сообщение об отсутствии событий в TodayCommandHandler (строка 99) THEN система SHALL использовать formatMessage()
6. WHEN формируется сообщение о корзине в TrashCommandHandler (строки 72, 193, 225) THEN система SHALL использовать formatMessage()
7. WHEN формируется сообщение об отсутствии событий в UpcomingEventsCommandHandler (строка 189) THEN система SHALL использовать formatMessage()
8. WHEN сообщения отправляются THEN Telegram API SHALL успешно распарсить MarkdownV2 без ошибок 400

### Requirement 4: Исправление жирного текста внутри строк formatMessage

**User Story:** Как пользователь, я хочу получать корректно отформатированные сообщения с жирным текстом, чтобы видеть информацию без ошибок парсинга.

#### Acceptance Criteria

1. WHEN используется жирный текст THEN система SHALL использовать метод bold() вместо `*текст*` внутри строки
2. WHEN формируется сообщение о создании события в UpdateProcessor (строки 694, 763, 1575) THEN система SHALL использовать bold() для заголовка
3. WHEN формируется статистика в StatsCommandHandler (строки 82-94) THEN система SHALL использовать bold() для чисел
4. WHEN сообщения отправляются THEN Telegram API SHALL успешно распарсить MarkdownV2 без ошибок 400

### Requirement 5: Использование правильных методов форматирования

**User Story:** Как разработчик, я хочу использовать правильные методы MarkdownFormatter, чтобы избежать ошибок экранирования в будущем.

#### Acceptance Criteria

1. WHEN формируется сообщение с форматированием THEN система SHALL использовать метод formatMessage для всего сообщения целиком
2. WHEN в сообщении используется жирный текст THEN система SHALL применять bold() только к части текста, которая должна быть жирной, и передавать результат в formatMessage()
3. WHEN в сообщении используется курсивный текст THEN система SHALL применять italic() только к части текста, которая должна быть курсивной, и передавать результат в formatMessage()
4. WHEN в сообщении используется моноширинный текст THEN система SHALL применять code() только к командам и техническим элементам, и передавать результат в formatMessage()
5. THE система SHALL NOT смешивать ручное экранирование с методами MarkdownFormatter
6. THE система SHALL NOT использовать ручную конкатенацию escape() + bold() + escape()
7. THE система SHALL NOT использовать `*текст*` внутри строк formatMessage()
