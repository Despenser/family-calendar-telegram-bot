# Документ проектирования: Реорганизация скриптов запуска

## Обзор

Проект реорганизации скриптов направлен на улучшение структуры проекта путём перемещения всех исполняемых скриптов из корневой директории в организованную структуру папок. Это повысит читаемость проекта и упростит поддержку скриптов для разных операционных систем.

## Архитектура

### Текущая структура
```
project-root/
├── clean.bat
├── clean.sh
├── logs.bat
├── logs.sh
├── start.bat
├── start.sh
├── stop.bat
├── stop.sh
├── docker-compose.yml

└── ...
```

```
project-root/
├── scripts/
│   ├── windows/
│   │   ├── clean.bat
│   │   ├── logs.bat
│   │   ├── start.bat
│   │   └── stop.bat
│   └── unix/
│       ├── clean.sh
│       ├── logs.sh
│       ├── start.sh
│       └── stop.sh
├── docker-compose.yml
├── .env
└── ...
```

## Компоненты и интерфейсы

### 1. Структура директорий

**scripts/windows/**
- Содержит все .bat файлы для Windows
- Скрипты выполняются из этой директории, но работают с файлами в корне проекта

**scripts/unix/**
- Содержит все .sh файлы для Linux/macOS
- Скрипты выполняются из этой директории, но работают с файлами в корне проекта

### 2. Модификации скриптов

Все скрипты должны быть обновлены для работы из новой локации. Основные изменения:

**Для Unix скриптов (.sh):**
- Добавить переход в корневую директорию в начале скрипта
- Использовать `cd "$(dirname "$0")/../.."` для перехода в корень проекта

**Для Windows скриптов (.bat):**
- Добавить переход в корневую директорию в начале скрипта
- Использовать `cd /d "%~dp0\..\.."` для перехода в корень проекта

### 3. Обновление документации

README.md должен быть обновлён с новыми путями:
- Windows: `scripts\windows\start.bat`
- Unix: `scripts/unix/start.sh`

## Свойства корректности

*Свойство - это характеристика или поведение, которое должно выполняться во всех допустимых выполнениях системы - по сути, формальное утверждение о том, что система должна делать. Свойства служат мостом между человекочитаемыми спецификациями и машинно-проверяемыми гарантиями корректности.*

### Свойство 1: Сохранение функциональности скриптов

*Для любого* скрипта из набора {start, stop, logs, clean}, выполнение скрипта из новой локации должно производить тот же результат, что и выполнение из старой локации.

**Проверяет: Требования 2.1, 2.2, 2.3**

### Свойство 2: Корректность путей

*Для любого* скрипта, все ссылки на файлы проекта (docker-compose.yml, .env) должны корректно разрешаться относительно корня проекта.

**Проверяет: Требования 2.1, 2.2, 2.4**

### Свойство 3: Полнота миграции

*Для всех* скриптов в корне проекта, каждый скрипт должен иметь соответствующую копию в новой структуре директорий перед удалением оригинала.

**Проверяет: Требования 1.4, 1.5, 4.1-4.8**

## Обработка ошибок

### Ошибка: Скрипт не может найти docker-compose.yml

**Причина:** Неправильный переход в корневую директорию

**Решение:** Проверить корректность команды `cd` в начале скрипта

### Ошибка: Скрипт не может найти .env файл

**Причина:** Неправильный рабочий каталог

**Решение:** Убедиться, что все docker-compose команды выполняются из корня проекта

### Ошибка: Права доступа для .sh файлов

**Причина:** После перемещения файлы могут потерять флаг исполняемости

**Решение:** Установить права доступа: `chmod +x scripts/unix/*.sh`

## Стратегия тестирования

### Unit тесты

Не применимо для скриптов оболочки.

### Интеграционное тестирование

**Тест 1: Проверка запуска из новой локации**
- Выполнить `scripts/windows/start.bat` (Windows) или `scripts/unix/start.sh` (Unix)
- Проверить, что контейнеры Docker успешно запустились
- Проверить, что нет ошибок о ненайденных файлах

**Тест 2: Проверка остановки**
- Выполнить `scripts/windows/stop.bat` (Windows) или `scripts/unix/stop.sh` (Unix)
- Проверить, что контейнеры успешно остановились

**Тест 3: Проверка просмотра логов**
- Выполнить `scripts/windows/logs.bat` (Windows) или `scripts/unix/logs.sh` (Unix)
- Проверить, что логи отображаются корректно

**Тест 4: Проверка очистки**
- Выполнить `scripts/windows/clean.bat` (Windows) или `scripts/unix/clean.sh` (Unix)
- Проверить, что очистка выполняется корректно

### Ручное тестирование

1. Проверить работу всех скриптов на Windows
2. Проверить работу всех скриптов на Linux/macOS
3. Проверить, что документация соответствует новой структуре
4. Проверить, что старые скрипты удалены из корня

## Детали реализации

### Шаг 1: Создание структуры директорий
```bash
mkdir -p scripts/windows
mkdir -p scripts/unix
```

### Шаг 2: Модификация Unix скриптов

Добавить в начало каждого .sh файла (после shebang и комментариев):
```bash
# Переход в корневую директорию проекта
cd "$(dirname "$0")/../.." || exit 1
```

### Шаг 3: Модификация Windows скриптов

Добавить в начало каждого .bat файла (после @echo off и комментариев):
```batch
REM Переход в корневую директорию проекта
cd /d "%~dp0\..\.."
```

### Шаг 4: Обновление README.md

Заменить все упоминания скриптов в корне на новые пути:
- `start.bat` → `scripts\windows\start.bat`
- `start.sh` → `scripts/unix/start.sh`
- И так далее для всех скриптов

### Шаг 5: Удаление старых скриптов

После проверки работоспособности удалить все .bat и .sh файлы из корня проекта.

## Миграционный план

1. Создать новую структуру директорий
2. Скопировать и модифицировать скрипты
3. Протестировать новые скрипты
4. Обновить документацию
5. Удалить старые скрипты из корня

## Обратная совместимость

Обратная совместимость не требуется, так как это внутреннее изменение структуры проекта. Пользователи должны будут обновить свои команды запуска согласно новой документации.
