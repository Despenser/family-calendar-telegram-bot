# Документ требований

## Введение

Данный документ описывает требования к улучшению процесса создания события через команду `/add_event` в Telegram боте семейного календаря. Цель улучшения - сделать процесс создания события более чистым и удобным, аналогично процессу редактирования события, где весь диалог происходит в одном сообщении бота, а сообщения пользователя удаляются из чата.

## Глоссарий

- **System** (Система): Telegram бот семейного календаря
- **User** (Пользователь): Авторизованный пользователь бота, создающий событие
- **Event_Draft** (Черновик события): Временный объект события со статусом DRAFT в базе данных
- **Creation_Message** (Сообщение создания): Единственное сообщение бота, которое обновляется на протяжении всего процесса создания события
- **User_Input_Message** (Сообщение пользователя): Текстовое сообщение, отправленное пользователем с названием или описанием события
- **Chat** (Чат): Telegram чат между пользователем и ботом

## Требования

### Требование 1: Удаление сообщения пользователя с названием события

**User Story:** Как пользователь, я хочу, чтобы мое сообщение с названием события удалялось из чата, чтобы чат оставался чистым и содержал только сообщение бота.

#### Критерии приемки

1. WHEN User отправляет текстовое сообщение с названием события, THEN THE System SHALL удалить User_Input_Message из Chat
2. WHEN User_Input_Message удалено, THEN THE System SHALL сохранить название в Event_Draft
3. WHEN название сохранено, THEN THE System SHALL обновить Creation_Message с подтверждением сохранения названия
4. IF удаление User_Input_Message не удалось, THEN THE System SHALL продолжить обработку и залогировать ошибку

### Требование 2: Удаление сообщения пользователя с описанием события

**User Story:** Как пользователь, я хочу, чтобы мое сообщение с описанием события удалялось из чата, чтобы чат оставался чистым и содержал только сообщение бота.

#### Критерии приемки

1. WHEN User отправляет текстовое сообщение с описанием события, THEN THE System SHALL удалить User_Input_Message из Chat
2. WHEN User_Input_Message удалено, THEN THE System SHALL сохранить описание в Event_Draft
3. WHEN описание сохранено, THEN THE System SHALL завершить создание события
4. IF удаление User_Input_Message не удалось, THEN THE System SHALL продолжить обработку и залогировать ошибку

### Требование 3: Обновление единого сообщения создания

**User Story:** Как пользователь, я хочу видеть весь процесс создания события в одном сообщении бота, чтобы легко отслеживать прогресс и не загромождать чат.

#### Критерии приемки

1. WHEN User начинает создание события через `/add_event`, THEN THE System SHALL создать Creation_Message
2. WHEN User выбирает дату через inline-календарь, THEN THE System SHALL обновить Creation_Message через editMessageText
3. WHEN User выбирает время через inline-кнопки, THEN THE System SHALL обновить Creation_Message через editMessageText
4. WHEN User отправляет название события, THEN THE System SHALL обновить Creation_Message через editMessageText с подтверждением
5. WHEN User отправляет описание события, THEN THE System SHALL обновить Creation_Message через editMessageText с финальным результатом
6. THE System SHALL сохранять messageId Creation_Message на протяжении всего процесса создания

### Требование 4: Сохранение messageId сообщения создания

**User Story:** Как система, я должна сохранять messageId сообщения создания, чтобы иметь возможность обновлять его на каждом шаге диалога.

#### Критерии приемки

1. WHEN System создает Creation_Message, THEN THE System SHALL сохранить messageId в Event_Draft
2. WHEN System обрабатывает User_Input_Message с названием, THEN THE System SHALL использовать сохраненный messageId для обновления Creation_Message
3. WHEN System обрабатывает User_Input_Message с описанием, THEN THE System SHALL использовать сохраненный messageId для обновления Creation_Message
4. WHEN создание события завершено, THEN THE System SHALL очистить сохраненный messageId из Event_Draft

### Требование 5: Обработка ошибок удаления сообщений

**User Story:** Как система, я должна корректно обрабатывать ситуации, когда удаление сообщения пользователя невозможно, чтобы не прерывать процесс создания события.

#### Критерии приемки

1. IF удаление User_Input_Message не удалось из-за отсутствия прав, THEN THE System SHALL залогировать предупреждение и продолжить обработку
2. IF удаление User_Input_Message не удалось из-за того что сообщение уже удалено, THEN THE System SHALL залогировать информацию и продолжить обработку
3. IF удаление User_Input_Message не удалось из-за сетевой ошибки, THEN THE System SHALL залогировать ошибку и продолжить обработку
4. THE System SHALL НЕ прерывать процесс создания события при ошибках удаления сообщений

### Требование 6: Совместимость с существующим процессом

**User Story:** Как разработчик, я хочу, чтобы новое поведение было совместимо с существующей логикой создания события, чтобы не нарушить работу других функций.

#### Критерии приемки

1. WHEN User выбирает тип события (персональное/семейное), THEN THE System SHALL работать как раньше
2. WHEN User выбирает дату через inline-календарь, THEN THE System SHALL работать как раньше
3. WHEN User выбирает время через inline-кнопки, THEN THE System SHALL работать как раньше
4. WHEN User нажимает кнопку "Пропустить" для описания, THEN THE System SHALL работать как раньше
5. THE System SHALL сохранять все существующие валидации и проверки безопасности

### Требование 7: Логирование операций

**User Story:** Как разработчик, я хочу видеть подробные логи операций удаления и обновления сообщений, чтобы иметь возможность диагностировать проблемы.

#### Критерии приемки

1. WHEN System удаляет User_Input_Message, THEN THE System SHALL залогировать userId, chatId и messageId
2. WHEN System обновляет Creation_Message, THEN THE System SHALL залогировать userId, chatId, messageId и текущий шаг
3. WHEN происходит ошибка удаления, THEN THE System SHALL залогировать тип ошибки и детали
4. THE System SHALL использовать уровень DEBUG для успешных операций и WARN/ERROR для ошибок
