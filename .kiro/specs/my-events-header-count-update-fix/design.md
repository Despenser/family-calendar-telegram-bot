# Дизайн: Обновление счетчика событий в шапке при удалении

## Обзор

Данный документ описывает дизайн решения для исправления бага, при котором счетчик активных событий в шапке первого сообщения команды /my_events не обновляется при удалении события посередине или в конце списка. Решение включает создание централизованного метода обновления шапки и его интеграцию во все точки удаления событий.

## Архитектура

### Текущая архитектура

```
MyEventsCommandHandler
  ├─ getUserEvents() - получает список событий
  ├─ buildMyEventsHeader() - формирует шапку
  └─ sendMessage() - отправляет сообщения

EventService
  └─ deleteEvent() - удаляет событие
      └─ передает флаг isMyEventsHeader следующему событию (только при удалении первого)
```

### Проблема

При удалении события посередине или в конце списка:
1. Флаг `isMyEventsHeader` остается у первого события
2. Счетчик в шапке не обновляется
3. Пользователь видит устаревшее количество событий

### Новая архитектура

```
MyEventsCommandHandler
  ├─ getUserEvents()
  ├─ buildMyEventsHeader()
  ├─ sendMessage()
  └─ updateMyEventsHeaderCount() - НОВЫЙ метод обновления шапки

EventService
  ├─ deleteEvent()
  │   ├─ передает флаг isMyEventsHeader
  │   └─ вызывает updateMyEventsHeaderCount() - НОВАЯ интеграция
  └─ completeEvent() - НОВАЯ интеграция
      └─ вызывает updateMyEventsHeaderCount()

TrashService
  └─ restoreEvent() - НОВАЯ интеграция
      └─ вызывает updateMyEventsHeaderCount()
```

## Компоненты и интерфейсы

### 1. MyEventsCommandHandler

#### Новый метод: updateMyEventsHeaderCount

```java
/**
 * Обновляет счетчик событий в шапке первого сообщения.
 * 
 * <p>Метод выполняет следующие действия:</p>
 * <ol>
 *   <li>Получает актуальное количество активных событий пользователя</li>
 *   <li>Находит событие с флагом isMyEventsHeader=true</li>
 *   <li>Формирует новую шапку с актуальным счетчиком</li>
 *   <li>Формирует полный текст сообщения (шапка + событие)</li>
 *   <li>Обновляет сообщение через Telegram API</li>
 *   <li>Сохраняет inline-кнопки события</li>
 * </ol>
 * 
 * <p>Если событие с шапкой не найдено или обновление не удается,
 * метод логирует ошибку и продолжает работу без выброса исключения.</p>
 * 
 * @param userId идентификатор пользователя
 */
public void updateMyEventsHeaderCount(Long userId)
```

### 2. EventService

#### Модификация метода deleteEvent

Добавить вызов обновления шапки после удаления события:

```java
public void deleteEvent(Long eventId, Long userId) {
    // ... существующая логика удаления ...
    
    // НОВОЕ: Обновляем счетчик в шапке
    myEventsCommandHandler.updateMyEventsHeaderCount(userId);
}
```

#### Модификация метода completeEvent

Добавить вызов обновления шапки после завершения события:

```java
public Event completeEvent(Long eventId, Long userId) {
    // ... существующая логика завершения ...
    
    // НОВОЕ: Обновляем счетчик в шапке
    myEventsCommandHandler.updateMyEventsHeaderCount(userId);
    
    return completedEvent;
}
```

### 3. TrashService

#### Модификация метода restoreEvent

Добавить вызов обновления шапки после восстановления события:

```java
public void restoreEvent(Long eventId, Long userId) {
    // ... существующая логика восстановления ...
    
    // НОВОЕ: Обновляем счетчик в шапке
    myEventsCommandHandler.updateMyEventsHeaderCount(userId);
}
```

### 4. TelegramMessageService

Использовать существующий метод `tryEditMessageText` для безопасного обновления сообщения:

```java
public boolean tryEditMessageText(Long chatId, Integer messageId, String newText, 
                                  InlineKeyboardMarkup replyMarkup)
```

Этот метод:
- Возвращает `false` если сообщение удалено/не найдено
- Возвращает `true` при успешном обновлении
- Не выбрасывает исключение при отсутствии сообщения

### 5. BotMessageBuilder

Использовать существующие методы:
- `buildMyEventsHeader(int eventCount)` - формирование шапки
- `buildEventMessage(Event event)` - формирование текста события

## Свойства корректности

*Свойство - это характеристика или поведение, которое должно выполняться для всех допустимых выполнений системы - по сути, формальное утверждение о том, что система должна делать. Свойства служат мостом между человекочитаемыми спецификациями и машинопроверяемыми гарантиями корректности.*

### Анализ критериев приемки

#### 1.1 WHEN пользователь удаляет событие посередине списка THEN система SHALL обновить счетчик событий в шапке первого сообщения

Мысли: Это правило, которое должно выполняться для любого события посередине списка. Мы можем создать список событий, удалить событие посередине, затем проверить что счетчик в шапке соответствует актуальному количеству событий.
Тестируемость: да - property

#### 1.2 WHEN пользователь удаляет последнее событие в списке THEN система SHALL обновить счетчик событий в шапке первого сообщения

Мысли: Это edge case - удаление последнего события. Генератор должен создавать списки с разным количеством событий.
Тестируемость: edge-case

#### 1.3 WHEN пользователь удаляет первое событие в списке THEN система SHALL передать шапку следующему событию с актуальным счетчиком

Мысли: Это edge case - удаление первого события. Это особый случай, который уже частично работает, но нужно проверить что счетчик актуален.
Тестируемость: edge-case

#### 1.4 WHEN система обновляет счетчик событий THEN система SHALL сохранить все остальные элементы шапки без изменений

Мысли: Это инвариант - при обновлении счетчика структура шапки должна сохраняться. Мы можем проверить что шапка содержит те же элементы (эмодзи, текст "Мои события") до и после обновления.
Тестируемость: да - property

#### 1.5 WHEN система обновляет сообщение с шапкой THEN система SHALL сохранить inline-кнопки первого события

Мысли: Это инвариант - inline-кнопки должны сохраняться при обновлении. Это важное свойство UI.
Тестируемость: да - property

#### 2.1 WHEN система обновляет счетчик событий THEN система SHALL использовать единый метод для всех сценариев обновления

Мысли: Это требование к архитектуре, не функциональное требование.
Тестируемость: нет

#### 2.2 WHEN метод обновления вызывается THEN система SHALL получить актуальное количество активных событий из базы данных

Мысли: Это правило о том, что метод должен получать данные из БД. Мы можем проверить что после вызова метода счетчик соответствует количеству записей в БД.
Тестируемость: да - property

#### 2.3 WHEN метод обновления вызывается THEN система SHALL найти событие с флагом isMyEventsHeader=true

Мысли: Это требование к реализации метода. Мы можем проверить что метод корректно находит первое событие.
Тестируемость: да - property

#### 2.4 WHEN событие с шапкой найдено THEN система SHALL обновить текст сообщения через Telegram API

Мысли: Это требование к взаимодействию с внешним API. Сложно тестировать без моков.
Тестируемость: нет

#### 2.5 WHEN обновление не удается THEN система SHALL залогировать ошибку и продолжить работу

Мысли: Это требование к обработке ошибок. Можно проверить что при ошибке система не падает.
Тестируемость: да - example

#### 3.1 WHEN пользователь удаляет событие через callback THEN система SHALL автоматически обновить счетчик в шапке

Мысли: Это интеграционный тест - проверка что callback вызывает обновление. Это правило для всех callback удалений.
Тестируемость: да - property

#### 3.2 WHEN пользователь удаляет событие через команду THEN система SHALL автоматически обновить счетчик в шапке

Мысли: Это интеграционный тест - проверка что команда вызывает обновление. Это правило для всех команд удаления.
Тестируемость: да - property

#### 3.3 WHEN система завершает событие автоматически THEN система SHALL автоматически обновить счетчик в шапке

Мысли: Это правило для автоматического завершения событий. Применяется ко всем событиям.
Тестируемость: да - property

#### 3.4 WHEN пользователь восстанавливает событие из корзины THEN система SHALL автоматически обновить счетчик в шапке

Мысли: Это правило для восстановления событий. Применяется ко всем восстановлениям.
Тестируемость: да - property

#### 3.5 WHEN обновление счетчика происходит THEN пользователь SHALL видеть изменения немедленно

Мысли: Это требование к UX - немедленность обновления. Сложно тестировать автоматически.
Тестируемость: нет

### Рефлексия свойств

Анализ избыточности:

1. **Свойства 1.1, 3.1, 3.2** - все проверяют что удаление вызывает обновление счетчика. Можно объединить в одно свойство: "Для любого удаления события счетчик обновляется"

2. **Свойства 1.4 и 1.5** - оба проверяют сохранение элементов при обновлении. Можно объединить: "При обновлении счетчика все элементы шапки и кнопки сохраняются"

3. **Свойства 2.2 и 2.3** - оба проверяют корректность работы метода обновления. Можно объединить: "Метод обновления корректно получает данные и находит первое событие"

4. **Свойства 3.3 и 3.4** - проверяют обновление при других операциях. Можно объединить с общим свойством об обновлении

После рефлексии остаются следующие уникальные свойства:

**Property 1: Обновление счетчика при изменении списка**
*Для любой* операции изменения списка событий (удаление, завершение, восстановление), счетчик в шапке должен соответствовать актуальному количеству активных событий
**Validates: Requirements 1.1, 3.1, 3.2, 3.3, 3.4**

**Property 2: Сохранение структуры шапки и кнопок**
*Для любого* обновления счетчика, все элементы шапки (эмодзи, текст "Мои события") и inline-кнопки первого события должны сохраняться
**Validates: Requirements 1.4, 1.5**

**Property 3: Корректность метода обновления**
*Для любого* вызова метода обновления, система должна получить актуальное количество событий из БД и найти событие с флагом isMyEventsHeader=true
**Validates: Requirements 2.2, 2.3**

## Обработка ошибок

### Сценарии ошибок

1. **Сообщение удалено пользователем**
   - Метод `tryEditMessageText` возвращает `false`
   - Логируется предупреждение
   - Работа продолжается без исключения

2. **Событие с шапкой не найдено**
   - Логируется предупреждение
   - Метод завершается без обновления
   - Работа продолжается

3. **Ошибка Telegram API**
   - Логируется ошибка с деталями
   - Работа продолжается без исключения
   - Пользователь не видит ошибку

4. **Нет активных событий**
   - Метод не выполняет обновление
   - Логируется информационное сообщение

### Стратегия обработки

```java
try {
    // Попытка обновления
    boolean updated = telegramMessageService.tryEditMessageText(...);
    if (!updated) {
        log.warn("Не удалось обновить шапку: сообщение не найдено или удалено");
    }
} catch (TelegramApiException e) {
    log.error("Ошибка при обновлении шапки: {}", e.getMessage(), e);
    // Продолжаем работу без выброса исключения
}
```

## Производительность

### Оптимизации

1. **Один запрос к БД**
   - Метод `getUserEvents()` уже оптимизирован
   - Возвращает только активные события

2. **Кэширование не требуется**
   - Операция выполняется редко (только при изменении списка)
   - Данные должны быть актуальными

3. **Асинхронность не требуется**
   - Обновление происходит в контексте транзакции
   - Пользователь ожидает немедленного результата

### Метрики

- Время выполнения: < 100ms
- Количество запросов к БД: 1
- Количество запросов к Telegram API: 1

## Безопасность

### Проверки доступа

1. **Проверка владельца события**
   - Выполняется в `EventService.deleteEvent()`
   - Только создатель может удалить событие

2. **Проверка messageId**
   - Telegram API автоматически проверяет права на редактирование
   - Бот может редактировать только свои сообщения

### Защита от ошибок

1. **Валидация входных данных**
   - Проверка userId на null
   - Проверка наличия событий

2. **Безопасное обновление**
   - Использование `tryEditMessageText` вместо `editMessageText`
   - Обработка всех исключений без прерывания работы

## Миграция данных

Миграция не требуется. Используются существующие поля:
- `Event.messageId` - уже заполняется при создании
- `Event.isMyEventsHeader` - уже используется для первого события
