# Требования: Фильтрация удаленных событий в списке "Мои события"

## Введение

Данная спецификация описывает исправление проблемы отображения удаленных событий в команде `/my_events`. В настоящее время удаленные события (со статусом `DELETED`) отображаются в списке "Мои события", что вводит пользователей в заблуждение и нарушает логику работы приложения.

## Глоссарий

- **System**: Telegram бот семейного календаря
- **User**: Пользователь бота
- **Event**: Событие в календаре
- **Event_Status**: Статус события (ACTIVE, DELETED, COMPLETED, DRAFT)
- **My_Events_Command**: Команда `/my_events` для просмотра событий пользователя
- **Trash**: Корзина для удаленных событий

## Требования

### Требование 1: Фильтрация удаленных событий

**User Story:** Как пользователь, я хочу видеть в списке "Мои события" только активные события, чтобы не путаться с удаленными событиями.

#### Критерии приемки

1. WHEN User запрашивает список своих событий через `/my_events`, THEN THE System SHALL возвращать только события со статусом ACTIVE
2. WHEN User запрашивает список своих событий через `/my_events`, THEN THE System SHALL исключать события со статусом DELETED
3. WHEN User запрашивает список своих событий через `/my_events`, THEN THE System SHALL исключать события со статусом DRAFT
4. WHEN User запрашивает список своих событий через `/my_events`, THEN THE System SHALL исключать события со статусом COMPLETED

### Требование 2: Доступ к удаленным событиям через корзину

**User Story:** Как пользователь, я хочу иметь доступ к удаленным событиям через отдельную команду корзины, чтобы при необходимости восстановить их.

#### Критерии приемки

1. WHEN User запрашивает корзину через `/trash`, THEN THE System SHALL возвращать только события со статусом DELETED
2. WHEN User просматривает корзину, THEN THE System SHALL отображать события, отсортированные по дате удаления (новые первыми)

### Требование 3: Согласованность фильтрации

**User Story:** Как разработчик, я хочу обеспечить согласованную фильтрацию событий по статусу во всех частях системы, чтобы избежать подобных проблем в будущем.

#### Критерии приемки

1. WHEN System получает события пользователя для отображения, THEN THE System SHALL явно указывать требуемый статус события
2. WHEN System использует методы репозитория для получения событий, THEN THE System SHALL использовать методы с фильтрацией по статусу
3. WHEN System отображает список событий, THEN THE System SHALL гарантировать, что события соответствуют ожидаемому статусу
