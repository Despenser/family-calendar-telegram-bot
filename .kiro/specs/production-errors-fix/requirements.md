# Требования: Исправление ошибок в продакшене

## Введение

Данный документ описывает требования для исправления критических ошибок, обнаруженных в логах Docker приложения Family Calendar Bot. Ошибки связаны с парсингом Markdown, обработкой callback-запросов и функциональностью фильтрации событий.

## Глоссарий

- **System** - Telegram бот Family Calendar
- **MarkdownV2** - Формат разметки Telegram для форматирования текста
- **Callback Query** - Запрос от Telegram при нажатии на inline-кнопку
- **Filter Command** - Команда /filter для фильтрации событий
- **Reply Keyboard** - Клавиатура с кнопками в Telegram

## Требования

### Требование 1: Исправление экранирования специальных символов в MarkdownV2

**User Story:** Как пользователь, я хочу получать корректно отформатированные сообщения о событиях, чтобы видеть всю информацию без ошибок парсинга.

#### Критерии приемки

1. WHEN система отправляет сообщение с предстоящими событиями THEN система SHALL корректно экранировать символ '(' в тексте "Предстоящие события семьи (30 дней)"
2. WHEN система отправляет сообщение "Мои события" THEN система SHALL корректно экранировать символ '.' в тексте сообщения
3. WHEN система форматирует любой текст для MarkdownV2 THEN система SHALL экранировать все зарезервированные символы: '_', '*', '[', ']', '(', ')', '~', '`', '>', '#', '+', '-', '=', '|', '{', '}', '.', '!'
4. WHEN система повторяет отправку сообщения после ошибки парсинга THEN система SHALL использовать исправленное экранирование при каждой попытке
5. WHEN система отправляет сообщение с reply клавиатурой THEN система SHALL применять корректное экранирование к тексту сообщения

### Требование 2: Обработка callback-запросов для фильтрации

**User Story:** Как пользователь, я хочу фильтровать события по категориям, чтобы видеть только нужные мне события.

#### Критерии приемки

1. WHEN пользователь нажимает кнопку 'filter_all' THEN система SHALL обработать callback и показать все события
2. WHEN пользователь нажимает кнопку 'filter_family' THEN система SHALL обработать callback и показать только семейные события
3. WHEN пользователь нажимает кнопку 'filter_personal' THEN система SHALL обработать callback и показать только личные события
4. WHEN система получает неизвестный callback data THEN система SHALL логировать предупреждение с telegramId пользователя
5. WHEN CallbackQueryDispatcher получает callback с префиксом 'filter_' THEN система SHALL направить его в соответствующий обработчик

### Требование 3: Реализация команды /filter

**User Story:** Как пользователь, я хочу использовать команду /filter, чтобы выбрать тип событий для отображения.

#### Критерии приемки

1. WHEN пользователь вводит команду /filter THEN система SHALL отобразить клавиатуру с опциями фильтрации
2. WHEN обработчик команды /filter выполняется THEN система SHALL возвращать непустой ответ с inline-кнопками
3. WHEN система отображает опции фильтрации THEN система SHALL предоставить кнопки: "Все события", "Семейные", "Личные"
4. WHEN пользователь выбирает фильтр THEN система SHALL сохранить выбор пользователя для последующих запросов
5. WHEN UpdateProcessor получает пустой ответ от обработчика команды THEN система SHALL логировать предупреждение с названием команды

### Требование 4: Обработка устаревших callback-запросов

**User Story:** Как система, я хочу корректно обрабатывать устаревшие callback-запросы, чтобы не генерировать ошибки в логах.

#### Критерии приемки

1. WHEN система получает ошибку "query is too old and response timeout expired" THEN система SHALL прекратить повторные попытки ответа
2. WHEN callback query устарел THEN система SHALL логировать информационное сообщение вместо ошибки
3. WHEN система отвечает на callback query THEN система SHALL проверять возраст запроса перед отправкой
4. WHEN все попытки ответа на callback query исчерпаны THEN система SHALL логировать финальную ошибку с callbackQueryId
5. IF callback query старше 30 секунд THEN система SHALL пропустить обработку без попыток ответа

### Требование 5: Улучшение логирования ошибок

**User Story:** Как разработчик, я хочу видеть детальную информацию об ошибках, чтобы быстро диагностировать проблемы.

#### Критерии приемки

1. WHEN система логирует ошибку парсинга MarkdownV2 THEN система SHALL включать telegramId, textPreview и полный текст ошибки
2. WHEN система логирует неизвестный callback data THEN система SHALL включать callback data и telegramId
3. WHEN система логирует пустой ответ от обработчика THEN система SHALL включать название команды
4. WHEN система исчерпывает попытки отправки THEN система SHALL логировать количество попыток и финальную ошибку
5. WHEN система обрабатывает исключение THEN система SHALL логировать stack trace для критических ошибок

### Требование 6: Предупреждения Flyway и Hibernate

**User Story:** Как разработчик, я хочу устранить предупреждения о версиях, чтобы обеспечить стабильность приложения.

#### Критерии приемки

1. WHEN приложение запускается с PostgreSQL 18.1 THEN система SHALL использовать совместимую версию Flyway
2. WHEN Hibernate инициализируется THEN система SHALL не требовать явного указания PostgreSQLDialect
3. WHEN приложение использует JPA THEN система SHALL явно отключить spring.jpa.open-in-view
4. WHEN система логирует предупреждения о версиях THEN система SHALL предоставлять рекомендации по обновлению
5. WHEN конфигурация содержит устаревшие параметры THEN система SHALL удалить их из application.yml
