# Документ требований

## Введение

Данный проект представляет собой Spring Boot 3.5.3 приложение, интегрированное с Telegram Bot API для создания семейного календаря. Система позволяет членам семьи планировать события, получать уведомления и просматривать расписание через Telegram бота. Бот использует Webhook для получения обновлений, PostgreSQL для хранения данных и Docker для развертывания.

## Глоссарий

- **Система**: Spring Boot приложение с интеграцией Telegram Bot API и PostgreSQL
- **Telegram Bot API**: Официальный API Telegram для создания ботов
- **Пользователь**: Член семьи, взаимодействующий с ботом через Telegram
- **Команда**: Текстовое сообщение, начинающееся с символа "/" (например, /start, /help)
- **Webhook**: HTTP endpoint для получения обновлений от Telegram в реальном времени
- **Update**: Объект, содержащий информацию о новом событии (сообщение, команда, callback)
- **Событие**: Запланированная активность с датой, временем и описанием
- **Семья**: Группа пользователей, имеющих доступ к общему календарю
- **TelegramId**: Уникальный идентификатор пользователя в Telegram
- **Maven**: Система управления зависимостями и сборки проекта
- **Git**: Система контроля версий
- **Docker**: Платформа контейнеризации приложений
- **PostgreSQL**: Реляционная база данных для хранения событий и пользователей

## Требования

### Требование 1

**Пользовательская история:** Как разработчик, я хочу иметь правильно настроенную структуру Spring Boot 3.5.3 проекта с Maven, PostgreSQL и Docker, чтобы начать разработку семейного календарь-бота с правильными зависимостями и конфигурацией.

#### Критерии приемки

1. WHEN проект создается, THEN Система ДОЛЖНА включать корректный pom.xml с зависимостями Spring Boot 3.5.3, telegrambots-spring-boot-starter 8.2.0, Spring Data JPA, PostgreSQL driver, Flyway 11.1.0, Testcontainers 1.21.2 и необходимыми плагинами Maven
2. WHEN проект инициализируется, THEN Система ДОЛЖНА содержать правильную структуру пакетов согласно best practices Java (controller, service, repository, model, config)
3. WHEN приложение запускается, THEN Система ДОЛЖНА успешно загружать Spring контекст и подключаться к PostgreSQL без ошибок
4. WHEN конфигурация читается, THEN Система ДОЛЖНА загружать параметры бота, базы данных и webhook URL из application.properties или переменных окружения
5. WHERE используется Docker, Система ДОЛЖНА включать Dockerfile и docker-compose.yml для контейнеризации приложения и PostgreSQL

### Требование 2

**Пользовательская история:** Как разработчик, я хочу безопасно хранить и загружать конфигурацию бота и базы данных, чтобы токены, пароли и секреты не попадали в систему контроля версий.

#### Критерии приемки

1. WHEN приложение запускается, THEN Система ДОЛЖНА читать токен бота, webhook URL и параметры БД из переменных окружения или application.properties
2. WHEN обязательные параметры отсутствуют, THEN Система ДОЛЖНА выбросить исключение с понятным сообщением об ошибке и остановить запуск
3. WHEN используется Git, THEN Система ДОЛЖНА исключать файлы с конфиденциальными данными через .gitignore
4. WHERE используются профили Spring, Система ДОЛЖНА поддерживать различные конфигурации для dev, test и prod окружений
5. WHEN конфигурация валидируется, THEN Система ДОЛЖНА проверять наличие всех обязательных параметров при старте приложения

### Требование 3

**Пользовательская история:** Как член семьи, я хочу зарегистрироваться в боте по моему Telegram ID, чтобы получить доступ к семейному календарю.

#### Критерии приемки

1. WHEN пользователь отправляет команду /start, THEN Система ДОЛЖНА проверить наличие пользователя в базе данных по Telegram ID
2. WHEN пользователь не найден в базе, THEN Система ДОЛЖНА отправить сообщение о необходимости регистрации или отсутствии доступа
3. WHEN пользователь найден в базе, THEN Система ДОЛЖНА отправить приветственное сообщение с информацией о доступных командах
4. WHEN регистрация выполняется, THEN Система ДОЛЖНА сохранить Telegram ID, имя пользователя и дату регистрации в PostgreSQL
5. WHEN команда обрабатывается, THEN Система ДОЛЖНА логировать событие с информацией о пользователе

### Требование 4

**Пользовательская история:** Как член семьи, я хочу создать событие в календаре с датой, временем и описанием, чтобы другие члены семьи знали о моих планах.

#### Критерии приемки

1. WHEN пользователь отправляет команду /add_event, THEN Система ДОЛЖНА запросить дату, время и описание события
2. WHEN пользователь вводит дату и время, THEN Система ДОЛЖНА валидировать формат и проверять, что дата не в прошлом
3. WHEN все данные введены корректно, THEN Система ДОЛЖНА сохранить событие в PostgreSQL с привязкой к пользователю и семье
4. WHEN событие сохранено, THEN Система ДОЛЖНА отправить подтверждение с деталями события
5. IF сохранение не удалось, THEN Система ДОЛЖНА логировать ошибку и уведомить пользователя

### Требование 5

**Пользовательская история:** Как член семьи, я хочу просмотреть все ближайшие события в календаре, чтобы знать планы семьи.

#### Критерии приемки

1. WHEN пользователь отправляет команду /upcoming_events, THEN Система ДОЛЖНА запросить из PostgreSQL все события семьи на ближайшие 7 дней
2. WHEN события найдены, THEN Система ДОЛЖНА отформатировать список с датой, временем, описанием и автором события
3. WHEN событий нет, THEN Система ДОЛЖНА отправить сообщение об отсутствии запланированных событий
4. WHEN список формируется, THEN Система ДОЛЖНА сортировать события по дате и времени
5. WHEN список отправляется, THEN Система ДОЛЖНА использовать Markdown форматирование для улучшения читаемости

### Требование 6

**Пользовательская история:** Как член семьи, я хочу получать уведомления о предстоящих событиях, чтобы не забыть о важных планах.

#### Критерии приемки

1. WHEN наступает время за 1 час до события, THEN Система ДОЛЖНА отправить уведомление всем членам семьи
2. WHEN уведомление формируется, THEN Система ДОЛЖНА включать дату, время, описание и автора события
3. WHEN уведомление отправлено, THEN Система ДОЛЖНА отметить в базе данных, что уведомление было отправлено
4. WHEN происходит ошибка отправки, THEN Система ДОЛЖНА повторить попытку до 3 раз
5. WHERE используется планировщик, Система ДОЛЖНА проверять предстоящие события каждые 5 минут

### Требование 7

**Пользовательская история:** Как член семьи, я хочу редактировать или удалять свои события, чтобы актуализировать календарь при изменении планов.

#### Критерии приемки

1. WHEN пользователь отправляет команду /my_events, THEN Система ДОЛЖНА показать список его событий с кнопками для редактирования и удаления
2. WHEN пользователь выбирает редактирование, THEN Система ДОЛЖНА позволить изменить дату, время или описание
3. WHEN пользователь выбирает удаление, THEN Система ДОЛЖНА запросить подтверждение перед удалением из базы
4. WHEN изменения сохранены, THEN Система ДОЛЖНА обновить запись в PostgreSQL и отправить подтверждение
5. WHEN пользователь пытается редактировать чужое событие, THEN Система ДОЛЖНА отклонить операцию с сообщением об ошибке

### Требование 8

**Пользовательская история:** Как разработчик, я хочу использовать Webhook для получения обновлений от Telegram, чтобы бот работал в реальном времени без постоянного опроса API.

#### Критерии приемки

1. WHEN приложение запускается, THEN Система ДОЛЖНА зарегистрировать Webhook URL в Telegram API
2. WHEN Telegram отправляет обновление на Webhook, THEN Система ДОЛЖНА обработать его асинхронно через REST controller
3. WHEN Webhook endpoint получает запрос, THEN Система ДОЛЖНА валидировать подпись запроса для безопасности
4. WHEN обработка завершена, THEN Система ДОЛЖНА вернуть HTTP 200 OK в течение 60 секунд
5. IF регистрация Webhook не удалась, THEN Система ДОЛЖНА логировать ошибку и остановить запуск

### Требование 9

**Пользовательская история:** Как разработчик, я хочу иметь централизованную обработку ошибок и логирование, чтобы все исключения обрабатывались единообразно.

#### Критерии приемки

1. WHEN происходит исключение в обработчике команды, THEN Система ДОЛЖНА перехватывать его и логировать с полным stack trace
2. WHEN ошибка перехвачена, THEN Система ДОЛЖНА отправлять пользователю дружественное сообщение об ошибке
3. WHEN происходит ошибка базы данных, THEN Система ДОЛЖНА логировать детали и уведомлять пользователя о временной недоступности
4. WHEN Telegram API возвращает ошибку, THEN Система ДОЛЖНА обрабатывать различные коды ошибок (rate limit, invalid token, etc.)
5. WHERE используется production окружение, Система ДОЛЖНА использовать структурированное логирование (JSON format)

### Требование 10

**Пользовательская история:** Как DevOps инженер, я хочу развернуть приложение с помощью Docker Compose, чтобы упростить установку и масштабирование.

#### Критерии приемки

1. WHEN выполняется docker-compose up, THEN Система ДОЛЖНА запустить контейнеры приложения и PostgreSQL
2. WHEN контейнеры запущены, THEN Система ДОЛЖНА автоматически применить миграции базы данных через Flyway или Liquibase
3. WHEN приложение в контейнере, THEN Система ДОЛЖНА использовать переменные окружения для конфигурации
4. WHEN PostgreSQL контейнер запущен, THEN Система ДОЛЖНА создать базу данных и пользователя автоматически
5. WHERE требуется персистентность, Система ДОЛЖНА использовать Docker volumes для хранения данных PostgreSQL

### Требование 11

**Пользовательская история:** Как разработчик, я хочу иметь миграции базы данных, чтобы схема БД версионировалась и применялась автоматически.

#### Критерии приемки

1. WHEN приложение запускается, THEN Система ДОЛЖНА автоматически применять миграции через Flyway или Liquibase
2. WHEN создается таблица users, THEN Система ДОЛЖНА включать поля: id, telegram_id (unique), username, first_name, family_id, created_at
3. WHEN создается таблица events, THEN Система ДОЛЖНА включать поля: id, user_id (FK), family_id, title, description, event_date, event_time, notified, created_at
4. WHEN создается таблица families, THEN Система ДОЛЖНА включать поля: id, name, created_at
5. WHEN миграция не удалась, THEN Система ДОЛЖНА остановить запуск и залогировать причину

### Требование 12

**Пользовательская история:** Как разработчик, я хочу иметь comprehensive документацию, чтобы новые разработчики могли быстро понять проект и развернуть его локально.

#### Критерии приемки

1. WHEN проект создается, THEN Система ДОЛЖНА включать README.md с описанием проекта, архитектуры и функционала
2. WHEN документация пишется, THEN Система ДОЛЖНА включать инструкции по локальному запуску с Docker Compose
3. WHEN описывается API, THEN Система ДОЛЖНА документировать все команды бота с примерами использования
4. WHEN описывается БД, THEN Система ДОЛЖНА включать ER-диаграмму и описание таблиц
5. WHERE требуется настройка Webhook, Система ДОЛЖНА предоставлять инструкции по настройке ngrok для локальной разработки
